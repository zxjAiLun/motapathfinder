## 1. Phase 0 — Four Narrow Correctness Repairs

### 1.1 Full route replay gate is now fail-closed
Before: the terminal verdict accepted `fullRouteStrictReplay === null`:

```js
roundStrictReplay && (!fullRouteStrictReplay || fullRouteStrictReplay.ok === true)
```

That is not a hard gate: a terminal route with no end-to-end replay evidence could still be
called strict-replay verified. Now:

```js
roundStrictReplay && fullRouteStrictReplay && fullRouteStrictReplay.ok === true
```

If a non-empty terminal route exists but full-route replay evidence does not, the verdict is
`DEPENDENCY_FEEDBACK_LOOP_REACHED_TERMINAL_REPLAY_UNVERIFIED`.

### 1.2 `commitSuccessfulLineage` now defaults OFF
Before: `config.commitSuccessfulLineage !== false` (default ON). After:

```js
const commitSuccessfulLineage = config.commitSuccessfulLineage === true;
```

Rationale (owner): the 5.27c A/B changed selection order in 27 of 41 rounds and reduced wall
time (117.3 s -> 85.1 s), but produced **no** capability or lineage-depth gain
(`MT3 false/false`, `exp 116/116`, `branches 214/214`, `depth 5/5`, `cumDec 10/10`). A single
wall-clock difference must not promote a mechanism to default. The mechanism stays
implemented and is enabled explicitly by the 5.27d experiment.

### 1.3 Exact final branch lifecycle sweep
Before: `advanceableBranchCount` read `lastEvaluationMap`, which is cleared every round and
only holds the most recent portfolio pass. Any open branch absent from that pass defaulted to
`advanceable = true`, so the metric was an **upper bound**, not a measurement.

Now, before the loop returns, every remaining open branch is evaluated once against the
**final** `attemptedExperimentKeys` (observation only: no local execution, no selection, no
route change). Unadvanceable branches are collapsed under the same monotonic rule used inside
the loop. Observable effect on the real tower: the previous `11 open / 11 advanceable` becomes
`11 evaluated -> 3 newly exhausted`, i.e. the true final counts are exact and the earlier
"all 11 are advanceable" reading was indeed wrong.

The sweep result is exported as `globalState.finalBranchLifecycleSweep`
(`evaluatedOpenBranchCount`, `advanceableBranchIds`, `newlyExhaustedBranchIds`).

### 1.4 Blocked-reason taxonomy split
Before: every branch with no `selectedAlternative` was labelled
`all-leading-prerequisites-blocked`, merging two different causes. After:

```ini
NO_CURRENTLY_EXECUTABLE_LEADING_PREREQUISITE
  = no alternative has an executable/complete leading prerequisite

ALL_EXECUTABLE_EXPERIMENTS_ALREADY_ATTEMPTED
  = executable prerequisites exist, but every experiment key was already burned
```

`evaluateCheckpoint()` now returns one of these two, and each exhausted branch records the
precise class in `exhaustedReason`.

## 2. Phase 1 — Stage Boundary Attribution

Method: `commitSuccessfulLineage = true`, `MT1 -> MT3`, 40 rounds, fixed work
(`maxTotalLocalExpansions 2000`, `localMaxExpansions 200`, `candidateLimit 8`). Each branch's
final evaluation (with each alternative's real counterfactual evidence: target floor, kind,
`actionGoal`, `status`, `damage`, `currentHp`, `reason`) is dumped via the new opt-in
`includeFinalEvaluations` path. No search behaviour changed.

### 2.1 Deep-branch classification

Deepest branches (`depth 4..5`, 121 branches, all on MT1):

| Bucket | Branches |
|---|---|
| `BLOCKED_BECAUSE_NONVIABLE` | **105** |
| `BLOCKED_BECAUSE_ALREADY_ATTEMPTED` | **16** |
| `MIXED` | 0 |

The split is real, not cosmetic:
- The 105 nonviable branches have alternatives whose leading evidence is
  `unbeatable-at-current-stats` (480 occurrences) or `lethal-at-current-hp` (8). **No**
  alternative exposes an executable prerequisite.
- The 16 already-attempted branches have genuinely `MT1 / viable-at-current-state`
  prerequisites that were exhausted by the attempt set. This is precisely the class the old
  merged label concealed.

Leading-prerequisite evidence histogram over deep branches:

```ini

status=viable-at-current-state      kind=prerequisite  floor=MT1  =  16

status=unbeatable-at-current-stats  kind=prerequisite  floor=MT1  =  16
```

### 2.2 Counterfactual parent-plan-tail direct probe (the decisive test)

The owner required that horizon work be implemented **only** if the parent plan's
automatically derived next prerequisite P1 can actually be reached from the child state while
replanning declares the branch blocked.

Result over the deepest blocked branches:

```ini
TAIL_NOT_LOST_BY_REPLANNING__NO_EXECUTABLE_PREREQUISITE_EXISTS_AT_CHILD_STATE = 5
TAIL_NOT_LOST_BY_REPLANNING__ALL_EXECUTABLE_PREREQUISITES_ALREADY_ATTEMPTED     = 1
REPLANNING_CONTEXT_LOSS_CANDIDATE                                              = 0
```

Sample of the probe:

```ini
branch-88  depth 5  floor MT1  leadingTargetFloor MT2  leadingStatus unbeatable-at-current-stats  currentHp 387  execAltAtChild 0
branch-89  depth 5  floor MT1  leadingTargetFloor MT2  leadingStatus unbeatable-at-current-stats  currentHp 667  execAltAtChild 0
branch-18  depth 4  floor MT1  leadingTargetFloor MT2  leadingStatus unbeatable-at-current-stats  currentHp 219  execAltAtChild 0
branch-213 depth 4  floor MT1  leadingTargetFloor MT1  leadingStatus viable-at-current-state      damage 5        execAltAtChild 1  (already attempted)
```

**The probe FAILS.** There is no case where a valid, automatically derived tail prerequisite
was reachable from the child state while replanning nonetheless declared the branch blocked.

### 2.3 Why 5.27c's attribution was too strong

Three of the owner's objections are confirmed by measurement:

1. The merged `all-leading-prerequisites-blocked` label did hide two causes; splitting it
   immediately separated 105 nonviable from 16 already-attempted branches.
2. "The remaining prerequisites are on MT2" does **not** imply "they are therefore not
   executable". `blockerEvidence()` computes a counterfactual battle evaluation at the target
   floor without requiring `state.floorId === MT2`; several deep branches do see MT2
   prerequisites, and the reason they are not executable is the **battle evaluation**
   (`unbeatable-at-current-stats`), not the floor distance.
3. The single-prerequisite executor is therefore not the observed blocker here: the
   prerequisite it *would* have been asked to chase is itself recorded as unattainable with
   the current hero stats.

## 3. Verdict and Consequence

```ini
FULL_ROUTE_REPLAY_GATE           = FAIL_CLOSED
COMMIT_SUCCESSFUL_LINEAGE_DEFAULT = OFF
FINAL_BRANCH_LIFECYCLE_SWEEP     = EXACT
BLOCK_REASON_TAXONOMY            = SPLIT_AND_OBSERVED

STAGE_BOUNDARY_EXHAUSTION        = ESTABLISHED
NONVIABLE_DOMINATES_DEEP_BLOCKS  = 105/121
ALREADY_ATTEMPTED_IS_A_REAL_MINORITY_CLASS = 16/121

PREREQUISITE_HORIZON_OR_REPLAN_CONTEXT_LOSS = NOT_ESTABLISHED (PROBE FAILED)
PREREQUISITE_HORIZON_LINE                   = NOT_AUTHORIZED_BY_EVIDENCE
```

Per the owner's pre-declared rule, when the probe fails:

```text
unbeatable / lethal
  -> resource preparation / feasibility issue

all viable experiments already attempted
  -> experiment identity / replanning issue
```

The measured class is dominated by **`unbeatable-at-current-stats`** (battle survivability at
the target floor with current hero resources), i.e. a **resource-preparation / feasibility**
gap, plus a smaller genuine **experiment-identity/replanning** subset (16 branches).

Phase 2 (automatic prerequisite tail continuation) was therefore **not implemented**. This is
the intended STOP_AND_RETURN outcome: the round ends with an attribution instead of another
forensic round.

```ini
PR_5_27D_PHASE2 = NOT_IMPLEMENTED
MT3_CAPABILITY_GATE_NOT_RUN = the horizon mechanism it gates does not exist
PREREQUISITE_HORIZON_LINE = NOT_SUFFICIENT_AS_FRAMED (and not needed to explain the block)
```

## 4. Non-Claims

- No claim that MT3 is impossible: this remains
  `UNKNOWN_UNDER_THIS_BUDGET_AND_PRUNING_POLICY`.
- No claim that the local executor can never span floors; only that in this run the
  prerequisites it would chase were unattainable with current stats.
- The 16 already-attempted branches are an **experiment-identity/replanning** signal worth its
  own narrow investigation, but they are not evidence for a multi-prerequisite horizon.
- No change to `transport-collapse.js`, retention, guided scheduler, DP priority, scoring,
  branch caps, or pruning.
