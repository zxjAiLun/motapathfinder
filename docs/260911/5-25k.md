## 0. 动机：一个会直接作用于 graph selection 的旧 correctness mismatch

`lib/mcgs.js` 自己的注释声明 aux reward 合同是 `MT1 = 0.0 … MT5 = 1.0`，但实现是：

```js
idx / terminalFloorIndex          // idx 与 terminalFloorIndex 都是 floorOrder 的“绝对索引”
```

而 `floorOrder` 前缀含 `sample0, sample1, sample2, New, World`，所以 MT1 实际得到 **0.556** 而非 0。

这不是“遥测数字不好看”：`auxProgress` 会被 backup 进每条 trajectory edge：

```text
edge.W_aux += auxProgress
qAux = W_aux / N_edge
score = qGoal + 0.10 * qAux + exploration
```

在 `goalReward` 恒为 0 时，`qAux` 是**唯一**能区分“这个分支曾经走得更深”的反馈之一。
绝对索引会同时：**(a) 给 MT1 一个本不该有的正 reward；(b) 压缩 MT1→MT2→MT3 的动态范围**，
从而正好削弱 UCT 对 prerequisite progress 的利用。

## 1. 修复（只改 reward geometry）

```text
startFloorIndex = floorOrder.indexOf(initialState.floorId)
goalFloorIndex  = floorOrder.indexOf(terminalGoal.floorId)
progress        = clamp((currentFloorIndex - startFloorIndex)
                        / (goalFloorIndex - startFloorIndex), 0, 1)
```

因为 region 就是 `floorOrder` 的**连续切片** `[startIndex..goalIndex]`，region ordinal 与索引差等价，
所以非连续塔也自动适用（无需另写 region-ordinal 分支）。

driver 从**真实 project 的 floorOrder** 计算并断言（不硬编码），实测：

```text
region = [MT1, MT2, MT3, MT4, MT5]   startIndex 5  goalIndex 9  span 4
MT1 = 0.00   MT2 = 0.25   MT3 = 0.50   MT4 = 0.75   MT5 = 1.00
```

**fail-closed**（实测 5/5 全部 throw，绝不退回全局索引）：

```text
missing start floor / missing goal floor / goal index <= start index / unmappable current floor / null start|goal
```

## 5. 结论

```ini
PR_5_25K = NO_MECHANISM_SIGNAL
AUX_PROGRESS_CONTRACT = REPAIRED (MT1=0.00 ... MT5=1.00, fail-closed, live in search)
REPAIRED_REWARD_CHANGES_FLOOR_REACH = NO
MCGS_LINE_STOP = TRUE          # 按评审预置：“若两臂仍 MT3=0/MT4=0/terminal=0，这条线就可以非常有把握地停”
STOP_AFTER_THIS_REQUALIFICATION = TRUE
```

**两层信息都拿到了**：

1. reward geometry 修复本身（CONTROL 也是 corrected-progress UCT）**没有**让任何一臂到达 MT3+；
2. 修复后的 UCT feedback + hierarchical proposer（TREATMENT）也**没有**。

因此可以排除“旧 reward normalization 把 graph feedback 压死了”这一解释。
结合 5.25i（on-policy 层面 prerequisite sequencing 是主因）与 5.25j（proposer ordering 不改变 reach），
本线结论是：

```ini
LOCAL_POLICY_PLUS_MCGS_GRAPH_MEMORY_INSUFFICIENT_FOR_PREREQUISITE_SEQUENCING = SUPPORTED
```

特别地：**没有**因为“reward 太弱”顺手把 `LAMBDA_AUX` 从 0.10 调大——本轮要区分的正是
“reward geometry 错” vs “MCGS 机制本身不足”，所以 λ/C/H 全部冻结。

### 5.2 仍保留的 caveat

- 运行仍**不是迭代可复现**的：同 180s/2GB 条件下 `stoppedReason` 在 time-limit 与 rss-limit 之间切换
  （本轮 3/8 rss-limit、5/8 time-limit）。因此**不**读 iteration 差异作信号；只有 reach verdict 稳定。
- 稳定性依据的**准确口径**（评审措辞修正）：

```ini
PR_5_25J_TO_5_25K_REQUALIFICATION = 24/24 SEARCHES MAXED_AT_MT2
  # 5.25j full run A 8 + 5.25j full run B 8 + 5.25k requalification 8
```

  **不得把它写成“5.25b→5.25k 全部 24/24”**：5.25b 的 H96 实验明确产生过 MT3 aux bucket
  （报告为 MT2/MT3 双峰），并不属于这 24 次。5.25b 的结论是 terminal feedback 恒为 0，
  而不是“所有搜索都只到 MT2”。
- 本结论限定于：**已验证的 reward 合同 + uniform rollout + H96 + 这套 graph/UCT + 这两个预算** 下的组合。
  它不是“MCGS 不可能解决魔塔”的一般性结论。
