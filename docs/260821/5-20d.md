## 两道防线

### 难度不得被当成手段

```text
DIFFICULTY_GUARD_TOKENS = ["I581", "I582", "level0"]
```

对每个候选 action 序列化后检查是否触及这三个难度杠杆，命中即从该次 expansion 过滤掉并计数；重放阶段再查一次。本轮实测 `difficultyGuardBlocked = 0` —— 达成路线的过程中难度 action **一次都没有被提供**，所以这条路线与"把游戏调低"无关。

### choice 只关无状态对话

`createNoStateChangeChoiceResolver` 只接受一种情形：选项中**恰好一个**分支不改变任何状态（空 action list）。不按坐标匹配，不按选项文字匹配。分支歧义（两个空分支）、没有空分支、空选项列表，一律拒绝并记录，最终体现为 `UNRESOLVED_REQUIRED_CHOICE` 而不是替玩家做决定。checker 另有一例专门证明它不会按"取消/确定"这类文字选择。本轮 `searchChoiceUnresolved = 0`。

## 严格重放的实现（须复核者留意）

第一次实现重放时我用"结构相等"在 `enumerateActions` 结果里找 route 条目，**失败**在 index 0。原因值得写下来：

```text
recorded route 混了两类东西：
  decision 条目（对象）  搜索真正选择的动作，以 normalized 形式 + fingerprint 记录
  auto: 条目（字符串）   runtime 在 autoPickup/autoBattle 下自己完成的拾取/战斗记账
                        例如 "auto:pickup:greenGem@MT1:7,6"

auto 条目永远不会出现在 enumerateActions 里——它不是可选动作，是运行时效果。
而 decision 对象的字段集也与 live enumerated action 不同（前者有 summary/fingerprint，
后者有 stance/path/travelState），所以结构相等本身就是错的判据。
```

改为复用既有可信机制 `route-store.resolveRecordedAction(simulator, state, decision)`：它在**当前 state** 上枚举候选，用 fingerprint 把记录的 decision 匹配到活候选上，最终 `applyAction` 施加的是**新枚举出来的对象**，不是记录里的 summary 字符串。这满足"禁止仅凭 summary 字符串执行"，且比字符串相等更强。

`auto:` 条目在重放时被跳过，由 runtime 在同样配置下自行重新执行。**证明它们被同样地重新执行的，是最终 `exactStateKey` 完全相同**——该 key 覆盖 hero、inventory、flags 与 floor mutations。若跳过 auto 条目是错的，这个 key 一定会分叉。本轮 `mismatches = []`，逐字段（hp/atk/def/mdef/exp/lv、inventory、flags、floorMutations）与 exactStateKey 全部一致。

这是本轮唯一一处需要复核者独立判断的设计取舍：我认为"decision 必须来自 live enumeration + auto 效果由最终状态键证明"是对合同的正确读法，但它确实不是"逐条 route 条目都过 enumerateActions"的字面读法。
