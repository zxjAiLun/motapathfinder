### 2. 双 agenda BinaryHeap

`O(frontier)` 线性扫描替换为两个二叉堆：`CONSERVE_HP` 与 `BREAK_BOTTLENECK`。

```text
每个合法 Pareto state 同时进入两个 heap；
pending map 是"是否仍可扩展"的唯一真相，保证每个 state 只被扩展一次；
pop 时跳过 stale entry（已扩展、已被 Pareto 淘汰、已失效）；
insertStaticParetoState 返回 evictedNodeIds，调用方据此 retire 其 agenda entry；
peakFrontier 统计 active pending state 数量，不统计含 stale entries 的 heap 长度。
```

`retiredStates` 作为新指标输出，用于确认淘汰确实生效。

### 3. 收紧 mode switch

```text
只有当前确实存在非零 blocker deficit 时，连续 4 次未改善才允许进入
BREAK_BOTTLENECK；deficit 为 [0,0] 或没有 blocker 时 stagnation 归零，
不得周期性切换。切换仍只影响 agenda，不影响动作合法性、Pareto 或状态 key。
```

效果：5.20a 的 invest 案例完整搜索从 **512 次** switch 降到 **1 次**。周期性 fallback 的行为消失。

该收紧暴露并修正了 5.20a invest fixture 的一个设计缺陷：原地图把 `armoured-wall` 放在 `toll-guard` 之后，因此囤血期间 frontier 上根本没有 blocker、deficit 恒为 `[0,0]`，收紧后不再切换、H2 失效。新地图把 `armoured-wall` 移到起始可达区域（把目标挡在身后、一开始就看得见），atk 宝石仍在 toll-guard 之后。这更贴近真实情形：**看得见的墙，打不过的墙**。

## Review 1（2026-08-21）— `CHANGES_REQUIRED`，阻塞 1 项

文件边界、语法、manifest 145/153、no-tower、diff 均正确；H1、H2、H3、H5、H6 的语义结果未发现丢解或非法路线。

**阻塞项：H4 内存闸门无法独立复现。** 复核方以 192 / 224 / 256MB 三种 V8 heap 上限连续运行，实际 RSS 分别约 **298.1 / 295 / 299MB**，均超过 `<256MB` 合同。本轮首次执行记录的 155MB（见上文 H4 段）**予以保留，不改写**。

三种 heap 上限给出几乎相同的 RSS，说明这不是单纯的机器基线差异。根因：两个 agenda 当时都保存**完整 state 对象**，某个 state 从一个 heap 展开后，另一个 heap 里的 stale entry 仍引用它的 `consumed` Set、`region` bitset、`frontierInteractions` 与 blocker 数组。因此 `peakFrontier=1533` 只统计 active pending states，**没有覆盖真正驻留在 heap 中的旧状态**。

另有一项非结果阻塞的状态边界：`invest-before-conserve` 完整搜索需 4096 expansions；`maxExpandedStates=4096` 时返回 `RESOURCE_LIMIT`，而 200000 时返回 `SOLVED(expanded=4096)`。原因是最后一次 expansion 若发生在 break mode，active pending 已空但 conserve heap 仍有 stale ticket，`limitReached` 被误判。应只由 `pending.size > 0` 决定。

## Iteration 2 — agenda retention + exact-budget 修复

不创建 Repair 子轮、不创建 authorization commit、继续使用原 milestone。未修改 fixture、搜索合法性、Pareto、mode policy、H1–H6 口径或预算；`package.json`、`solver-manifest.json`、fixtures 均未改动。

### 1. Agenda 只保存轻量 ticket

```text
heap 元素由完整 state 改为 { id, rank }（新增导出纯 helper buildAgendaTicket）。
完整 state 只由 pending: Map<id, entry> 持有。
admit(entry)  → pending.set + 两个 heap 各 push 一个 ticket
popNext()     → heap 取 ticket，用 pending.get(ticket.id) 解析；取不到即 stale，继续 pop
heap 内不再出现 hero / consumed / region / frontierInteractions / deficit / entry 引用
```

结果：state 一离开 pending 即可被回收，不再被另一个 agenda 的 stale entry 钉住。

### 2. BinaryHeap.rebuild()

当两个 heap 元素总数 > `pending.size * 4 + 4096` 时，从当前 pending entries 一次性重建两个 heap，只保留 active tickets。纯内存整理：rank、pending membership、pop 次序均不变（每个 rank 末位是 node id，构成全序，相同 rank 仍由 node id 确定性打破平局）。新增输出指标 `agendaRebuilds`。

实测重建次数：scale A = 3，scale B = 2，invest 完整搜索 = 0。

### 3. 预算边界

`limitReached` 严格等于 `pending.size > 0`，不再查看任一 heap 的物理 size（heap 可能只剩 stale tickets）。

```text
invest-before-conserve 完整搜索 expanded = 4096
  budget 4096 → SOLVED，goal archive 与 generous run 完全相同
  budget 4095 → RESOURCE_LIMIT
```

已作为锁定 regression 写入 checker。

### 4. 额外的内存归因（诚实记录：超出复核方点名的 heap retention）

Ticket 化之后本机 RSS 为 124–127MB，但复核方观测值约为本机的 1.9 倍（其 298MB vs 本机同版本 155MB），按该比例外推仍会逼近 230MB 目标线。因此进一步做了三项**纯内存**处理（不改算法、不加磁盘、不加 worker、不改预算）：

```text
a  computeStaticReachableRegion 的 visited 缓冲区改为复用
   （它从不逃逸本次调用；每个 generated state 都会分配一个是纯 churn）
b  solver entry 不再保留 region 与 deficit.blockers
   （region 只用于构建一次 structural key；ranking 只读两个 deficit 数字）
c  structural key 的 region bitset 由「每格 1 字符」改为「每字符 4 格」十六进制打包
   （精确且单射编码；已用全部 4096 个 12-bit 模式验证无碰撞）
   22x7 地图的 key 长度 160 → 45 字符
```

诊断依据（本机实测）：强制 GC 后 heapUsed 仅 **4MB**、RSS 仍 130MB —— 说明内存并非活跃驻留，而是 **V8 为吸收每状态分配 churn 而增长的 heapTotal**（solve 后 heapTotal 82MB / heapUsed 28.5MB）。`arrayBuffers` 仅 0.2MB，排除了外部 ArrayBuffer 的可能。scale A 单例 RSS 由 131.9MB 降至 **109.7MB**，heapTotal 由 86.3MB 降至 60.3MB。

三项处理均不改变结果：scale A 仍为 `SOLVED / hp=393 / expanded=18286 / peakFrontier=1533`。
