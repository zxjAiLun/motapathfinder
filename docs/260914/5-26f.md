## Problem and existing evidence

PR-5.26e established on the fixed-work MT4 diagnostic:

```ini
PRIORITY_MAP = ABSENT_ON_THIS_HARNESS
CURRENT_MT4_GUIDED_SCORE_DISTRIBUTION = {"100": 8916}
EQUAL_SCORE_HEAP = NON_FIFO
EQUAL_SCORE_BACKLOG = OBSERVED
EQUAL_SCORE_SERVICE_ORDER = AN_ACTUAL_SEARCH_POLICY_DIMENSION
```

Every guided admission on the capability harness has the same fallback score `100`, and the binary heap had no equal-score tie-break: insertion stops at `parent.score >= child.score` and pop only sinks on a strict `>`, so equal-score service order was an artifact of heap array mechanics. A later equal-score node could be served before an older one.

## What this round is and is not

```ini
TARGET = DEFINED_EQUAL_SCORE_GUIDED_SERVICE_SEMANTICS
NOT_TARGET = MAKE_CP16_EXPAND
STABLE_FIFO_WILL_RESCUE_CP16 = NOT_PREDICTED
```

cp#16 is a telemetry probe, not a policy target. It registered at expansion 10352 with **327 other** equally-scored live guided nodes, so strict oldest-first should if anything serve it *later*. No capability success criterion was declared on any single oracle key. The question is whether a stable, explainable, registration-consistent service contract changes overall search capability.

## Contracts and invariants

- `stableGuidedTieBreak` defaults to `false`. Every existing caller is unchanged.
- With the flag off the comparator must be **byte-identical** to pre-5.26f. It is: `guidedComesBefore(a,b,false)` returns `false` on equal scores, so push and pop reduce to exactly the original `>=` / `>` comparisons.
- A higher score always wins in both modes. This is a tie-break, not a plain FIFO.
- The flag affects the guided heap only. Retention, `pendingRank`, the neutral lane, the cap, the frontier and the skyline are untouched.
- `ORACLE_KEYS_AFFECT_SEARCH_DECISIONS = FALSE`. Oracle keys remain post-hoc callback filters.
- Wait age is computed at emission time and never stored in search state.

## Implementation

`lib/transport-collapse.js`:

```js
function guidedComesBefore(a, b, stableTieBreak) {
  if (a.score !== b.score) return a.score > b.score;
  if (!stableTieBreak) return false;
  return (a.pendingSeq ?? 0) < (b.pendingSeq ?? 0);
}
```

`guidedHeapPush` / `guidedHeapPop` take `(heap, entry, stableTieBreak)` and use `guidedComesBefore` in place of the inline score comparisons. Heap entries are now `{ nodeId, score, pendingSeq }`; `pendingSeq` is ignored unless the flag is on, and `pendingSeq` is the same registration counter the retention trim already uses, so the semantics match the existing same-rank insertion-order rule.

Telemetry (opt-in `emitGuidedServiceTelemetry`): the `expanded` event now also carries `guidedAdmitted`, `guidedPendingSeq` and `guidedWaitAgeAtExpansion = expansion - registeredAtStrategicExpansion` for guided-admitted nodes, plus `stableGuidedTieBreak` on the result. This lets an audit report a wait-age distribution without retaining any per-node map.

Harness plumbing: `--stable-guided-tie-break` on `check-bounded-candidate.js`, `check-bounded-transfer.js` (including child re-exec) and `audits/flat-search/audit-pr525t-oracle-survival.js`.

## Results

The three pre-declared gates pass. The mechanism does what it was specified to do, and the wait-age distribution shows the intended effect directly:

- **Legacy guided service had a very long wait tail.** Median wait age 6 but p95 187 and max 6397: most guided-admitted nodes were expanded almost immediately (the "new node preference" of the non-FIFO heap), while some older guided node waited 6397 expansions before being expanded.
- **The stable contract compresses that tail.** Median 867, p95 1243, max 1441.
- **Prefix survival improved substantially.** `LAST_ORACLE_CHECKPOINT_EXPANDED` moved 14 → 28 and the first loss 16 → 29; `NEVER_GENERATED` fell from 35-37 to 23.

### Correction: what the wait-age telemetry does and does not measure

`guidedWaitAgeAtExpansion` is recorded on the `expanded` event and only for nodes that were **guided-admitted**; it does not record which selection lane served a given expansion. So it cannot establish that *starvation* was removed — only that the expansion delay distribution of guided-admitted nodes changed shape. The earlier wording `GUIDED_STARVATION_TAIL = REMOVED` is **retracted as too strong**. The defensible statement is:

```ini
EXPANDED_GUIDED_ADMITTED_WAIT_TAIL = COMPRESSED   (max 6397 -> 1441)
SERVICE_LATENCY_DISTRIBUTION = REDISTRIBUTED     (med 6 -> 867, p95 187 -> 1243)
"STARVATION_REMOVED" = NOT_FULLY_ESTABLISHED
```

The redistribution is the interesting part: the stable contract does not only shorten the tail, it lengthens the *median*. A worst case of 6397 becoming 1441 while the median goes 6 → 867 is one distribution being traded for another, not a strict improvement. Supporting numbers: legacy median 6 / p95 187 / max 6397 versus stable median 867 / p95 1243 / max 1441.

### Two side effects that must not be buried

1. **The blast radius is larger than "who is served first".** `guidedAdmittedGenerated` at fixed work rose 8916 → 15792 (about 1.77x) and `candidatesDropped` 13580 → 26371. Guided admission is gated by the resource skyline, and the skyline set is order-dependent (first-inserted wins the dominance test), so changing expansion order changes **which nodes are admitted at all**. The tie-break therefore alters the admission funnel, not only the service order. This is the reason for effect 2.
2. **The stable arm is markedly more memory-hungry.** Peak RSS at fixed work rose 1789.9MB → 2030.4MB, and both the MT4 run (2050.4MB) and the survival audit (2049MB) terminated on **RSS**, not on wall time. More admissions mean more retained candidates and more registry state. At fixed work the stable arm also reached a shallower strategic depth (38 → 29) while covering more of the oracle prefix.

Consequently the honest summary is a trade, not a win:

```ini
STABLE_EQUAL_SCORE_ORDER_ACTIVE = TRUE
EXPANDED_GUIDED_ADMITTED_WAIT_TAIL = COMPRESSED
SERVICE_LATENCY_DISTRIBUTION = REDISTRIBUTED
"STARVATION_REMOVED" = NOT_FULLY_ESTABLISHED
ORACLE_PREFIX_SURVIVAL = IMPROVED (first loss 16 -> 29)
GUIDED_ADMISSION_FUNNEL = CHANGED (8916 -> 15792 at fixed work)
RSS_COST_AT_FIXED_WORK = INCREASED (1790 -> 2030 MB)
MT4 = NOT_RESOLVED (RSS-limited, 11329 expansions in 103.6s)
```

## Process note - one accidental legacy control

An intermediate execution of the survival audit had the `--stable-guided-tie-break` flag passed but the declaration missing from the script, so the search actually ran with the mechanism **off**; the run then crashed while printing. It is retained rather than deleted because it is a valid same-harness legacy control: 11650 expansions, `LAST_ORACLE_CHECKPOINT_EXPANDED = 14`, first loss 16 — matching the earlier legacy runs. The corrected run with the flag actually enabled is the one reported above. The script now declares and threads the flag, and the A/B audit's `OFF_ARM_MATCHES_5_26E_ANCHOR` gate is the durable guard against this class of mistake.

**Reading rule for the comparison table above:** the `11650 expansions` row is `ACCIDENTAL_LEGACY_SURVIVAL_CONTROL`, **not** the Phase-2 fixed-work OFF arm. The true Phase-2 OFF fixed-work arm is **12000 expansions** (guided 8125 + neutral 3875). The two rows are different runs of different harnesses; no conclusion in this document depends on comparing them. The accidental control is listed because its numbers conveniently landed near the other survival-audit expansion counts, which is exactly the kind of coincidence that should be labelled rather than left to look like a matched arm.

## Known limitations

- Single run per arm and per gate. No repeatability claim.
- MT4 is unresolved and memory-terminated; a miss under this budget is `UNKNOWN_UNDER_THIS_BUDGET_AND_PRUNING_POLICY`, not impossibility.
- The admission-funnel side effect means this mechanism cannot be described as a pure service-order change. Separating "service order" from "skyline admission order" would be its own question.
- Prefix survival against a known route is not the same as capability: a longer surviving oracle prefix is not a found route.
