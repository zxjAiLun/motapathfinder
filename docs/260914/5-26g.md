## 1. The defect being repaired

PR-5.26f changed only *which* equal-score guided node is popped. That was enough to change the number of guided admissions by ~1.77x at fixed work, which pushed MT4 into the RSS limit and raised `candidatesDropped`. The owner's diagnosis, which this round implements, is the mechanism behind that amplification:

`skylineSet.query()` asks only **"did any previously SEEN state dominate this one?"** and `skylineSet.insert()` is **append-only**. Nothing ever revokes a guided admission that a later, stronger state supersedes. Therefore:

```text
weak arrives first, strong arrives second -> {weak, strong} both guided
strong arrives first, weak arrives second -> {strong} guided, weak rejected
```

`GUIDED_ACTIVE_MEMBERSHIP = ARRIVAL_ORDER_SENSITIVE`. The active guided set is a function of generation order, and generation order is a function of service order. That is why a tie-break change was able to move the admission funnel.

## 2. Mechanism as implemented

`lib/transport-collapse.js`:

- `retroactiveGuidedSkylineDemotion` - **opt-in**, `config.retroactiveGuidedSkylineDemotion === true`, default **off**.
- Grouping uses **the skyline's own group key** (`skylineSet.query()` returns `structuralKey`), i.e. `buildStructuralStateKey` over the child state. This is deliberate: the repair must cancel the admission heuristic's asymmetry using the same notion of "same state", not introduce a second one.
- On a guided admission, if `retroactiveGuidedSkylineDemotion` is on and the skyline was consulted:

  1. the new node is recorded in `guidedGroups[structuralKey]`;
  2. every member of that group that is **live** and **dominated** by the new node's resource vector is demoted.

- Demotion sets exactly three things plus bookkeeping:

  ```js
  peer.guidedAdmitted = false;
  peer.guidedRetroDemoted = true;
  peer.rankValue = null;              // recompute; never hard-write rank 30
  members.delete(peer.id);
  noteGuidedRemoved();                 // live-guided counter
  guidedRetroDemotions += 1;
  ```

- **Not a prune.** The demoted node stays in `pending`, stays `closed = false`, stays in the neutral queue, and is still expanded - just from the neutral lane instead of the guided lane. `HARD_PRUNING = FALSE`.
- **Permanent for guided eligibility: no re-promotion.** No code path re-admits a node to the guided heap, and the existing skyline contract already says "once a dominator has been seen, a later weak variant never gets guided admission". Re-promoting would amount to inventing a live dynamic skyline rather than repairing an arrival-order asymmetry. `guidedRetroDemoted` is retained as an audit flag so a demoted node is distinguishable from a never-guided one.
- **Stale guided-heap entries are skipped, not deleted.** Arbitrary delete in a binary heap is easy to get wrong, so a demoted node's heap entry is left in place and the guided pop is feature-gated (off = byte-identical):

  ```js
  const staleDemoted = retroactiveGuidedSkylineDemotion && candidate
    && candidate.closed !== true && candidate.guidedAdmitted !== true;
  if (staleDemoted) guidedHeapStaleDemotionSkips += 1;
  if (candidate && !candidate.closed && !staleDemoted) { ... }
  ```

### 2.1 Liveness, and why it is a single mechanism

Demotion must never touch a node that cannot be served. An **expanded** node has had its state released (`node.state = null`), so dereferencing it would throw; a **dropped** node is no longer in the pending pool.

Liveness is therefore decided by **`livePendingIds`**, the pre-existing mirror of `pending` that the enqueue/snapshot telemetry already maintains at registration, expansion, and trim. `livePendingIds` is now also created when this flag is on. That gives one source of truth, and it means the removal bookkeeping cannot itself be the correctness mechanism.

`guidedGroups` is still allowed to retain ids of dead nodes, and a bounded sweep reclaims them: at trim, if the tracked-id count exceeds `guidedGroupSweepThreshold` (default `max(256, 4 * cap)`, overridable via `config.guidedGroupSweepThreshold`), the map is cleared and rebuilt from the live pending set using `node.retroGuidedGroupKey` (remembered at admission so the key is never recomputed from released state). Membership is therefore bounded by the live pool, not by total admissions.

### 2.2 New telemetry

Result fields: `retroactiveGuidedSkylineDemotion`, `guidedRetroDemotions`, `guidedRetroDemotionScans`, `guidedGroupTrackedIds`, `guidedGroupSweeps`, `guidedGroupSweepThreshold`, `guidedHeapStaleDemotionSkips`, `guidedActivePeak`, `liveGuidedPendingAtEnd`, `rank10PendingAtEnd`, `retroDemotedStillPendingAtEnd`. Lifecycle event: `guidedRetroDemotion`.

Two honest annotations:

- `guidedRetroDemotionScans` is incremented per admission whose group was non-empty, and the new child is added to the group **before** the scan, so it is **always** non-empty. `guidedRetroDemotionScans == guidedAdmittedGenerated` whenever the skyline is consulted - it is not a selectivity measure and must not be read as one.
- `guidedActivePeak` counts the **transient** admission that is demoted microseconds later. It is an occupancy peak, not a peak of useful work.
- `rank10PendingAtEnd` is derived from `rankClassOf()`, not from the flag, so a divergence between "is guided" and "is rank 10" would surface rather than hide.
- `liveGuidedPendingAtEnd` / `rank10PendingAtEnd` are computed by walking `pending` (the authoritative pool), **not** from the running counter, so they cannot drift with the counter.

### 4.1 What actually happened, stated carefully

The mechanism fired, and it did the specified thing. It did **not** do the thing it was aimed at.

1. **The guided backlog it was supposed to relieve is unchanged.** `liveGuidedPendingAtEnd` is 1022 (OFF) vs 1018 (ON) against a candidate cap of 1024, and `guidedActivePeak` is 1043 in both arms. Out of 3152 demotions, only **1** demoted node was still pending at the end (`retroDemotedStillPendingAtEnd = 1`). The pending pool is saturated with rank-10 guided nodes in both arms; demotion frees a slot that the next admission immediately refills. The mechanism changes **who** holds guided status, not **how many** nodes hold it.

   > This is the substantive finding of the round. The memory driver is not "the wrong nodes are guided" but "almost every retained candidate is guided, and admissions arrive faster than the pool drains". A membership-level repair cannot move that number.

2. **The RSS outcome is a thin signal, not a large regression.** 2050.9 MB vs 2029.8 MB peak is **+1.0%**, and the OFF arm was itself within 1% of the 2048 MB ceiling. Both arms sit on the RSS boundary; which one crosses it first is decided by a margin far smaller than run-to-run noise on this workload. What can be said is that the repair did **not create headroom**, even though it admitted ~9% fewer nodes.

3. **Per-unit cost went up.** ON did 9193 expansions in 479.3 s (52.1 ms/exp) versus OFF's 12000 in 453.3 s (37.8 ms/exp), and its trim churn per expansion rose from 2.20 to 2.43 drops/exp. The modified expansion order explores a different, deeper part of the space (`deepestStrategicDepth` 32 vs 29) with more churn per unit work.

4. **Blast radius again.** `guidedAdmittedGenerated` moved 15792 -> 14322 (**-9.3%**) even though the only difference is guided membership. The first-inserted-wins skyline means changing which nodes are guided changes which nodes are later generated. So the effect is still larger than its name: it is not confined to guided membership.

5. **The arms are not work-matched.** ON terminated at 9193 expansions, OFF at 12000, so `depth 32 vs 29` and any other work-normalized comparison between them is **not** an apples-to-apples capability reading. `ARMS_NOT_WORK_MATCHED = TRUE`.

6. **The mechanism does not touch the oracle checkpoints.** cp#14 and cp#16 were registered and expanded in both arms and were **not** retro-demoted in either.

```ini
MT4_CAPABILITY                = NOT_RUN (pre-declared stop)
DEFAULT_ENABLEMENT            = NO (opt-in, default off)
```

The honest reading of the round: the repair is correct and it works exactly as specified at the level it operates on, but the level it operates on is **not** the binding one. The guided pool is admission-rate-driven under cap saturation, so demoting members cannot reduce the guided population. The binding quantity is the **guided admission rate into a saturated pool**, which this round's evidence now points at directly (1018-1043 live guided nodes against a 1024 cap, with 3152 demotions leaving exactly 1 demoted node in the pool at the end).

## 8. Next-round candidate (not authorized)

The evidence points at a different question than the one this round asked: **guided admission into a capped pool**. With `liveGuidedPendingAtEnd` at 1018-1022 of a 1024 cap, the pool is effectively all-guided; a mechanism that decides *which* nodes are guided cannot change that. The candidate direction is an admission-rate or pool-composition contract (e.g. what fraction of the capped pool may hold guided status, or whether guided admission should be gated by something other than first-inserted-wins skyline dominance) - **not** another membership tie-break.

This is recorded as a candidate only. No work is authorized pending owner review.
