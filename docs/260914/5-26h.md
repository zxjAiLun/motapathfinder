# PR-5.26h - Guided Pool Saturation Composition and Flow Audit

- Date: 2026-09-14
- Base: `83128ce` (PR-5.26g, closed)
- Status: `IMPLEMENTED / DIAGNOSTIC_COMPLETE / SEARCH_POLICY_CHANGE_NONE`
- Owner authorization: PR-5.26h as **GUIDED_POOL_SATURATION_COMPOSITION_AND_FLOW_AUDIT**, pure diagnostic, with the run design, telemetry list, and NO-list specified in the 5.26g review.
- Headline: **the ~99%-rank-10 pool is created by `stableGuidedTieBreak`, not pre-existing.** At matched work the legacy arm never exceeds a 5.6% rank-10 occupancy and ends with 40/1024 rank-10 slots, while the stable arm reaches 100% and ends with 1024/1024.

---

## 1. The question

PR-5.26g observed that the capped pending pool sat at 1018-1022 rank-10 (guided-admitted) slots out of 1024, and that 3152 demotions left exactly 1 demoted node in the pool. Three things were explicitly left unmeasured by that round:

```ini
CUMULATIVE_GUIDED_ADMISSIONS = NOT_COMPARABLE_ACROSS_PHASE2_ARMS
"IMMEDIATE_REFILL_AFTER_EACH_DEMOTION" = NOT_MEASURED
FLOW_IMBALANCE_CAUSE = NOT_YET_DIRECTLY_MEASURED
```

And one scoping gap: both 5.26g arms ran with `stableGuidedTieBreak` **ON**, so the saturation was observed entirely inside the stable configuration. This round measures:

1. what the roughly 1020 slots actually contain (identity vs variant multiplicity, structural grouping, dominance composition);
2. the four guided flows over a matched-work window (admission, removal by expansion, removal by drop, demotion);
3. whether saturation is a baseline property or a stable-tie-break property.

## 2. Design

Pure diagnostic. `SEARCH_POLICY_CHANGE = NONE`, `ORACLE_USE = NONE` (no oracle key is read at all this round), no quota, no reserve, no per-identity or per-group cap, no cap or budget change, no frontier patch.

Two child-process arms, **matched work**:

```ini
MAX_EXPANSIONS = 8000
MAX_RUNTIME_MS = 0
MAX_RSS_MB = 2048
CAP = 1024
rank20DynamicPareto = ON
neutralParetoSubstitution = ON
retroactiveGuidedSkylineDemotion = OFF      # 5.26g closed; must not be combined
ARM_LEGACY: stableGuidedTieBreak = OFF
ARM_STABLE: stableGuidedTieBreak = ON
```

8000 is the owner-specified diagnostic observation window: below the 9193 at which the 5.26g ON arm hit the RSS ceiling, and long enough for cap saturation to be observable. It is not a capability budget. If either arm terminated on RSS before 8000 the instruction was STOP with no retry - **neither arm did**: both reached 8000 with `stoppedReason = expansion-limit` at 957.0 MB (legacy) and 1333.6 MB (stable).

### 2.1 Telemetry added (aggregate only, opt-in, default off)

`config.emitGuidedPoolTelemetry`, read-only, no per-node events, at most two composition snapshots per run:

- occupancy per trim (on the **post-trim** pool): kept rank 0/10/20/30 counts, rank-10 fraction of cap, min/mean/max over trims, count of trims at >= 90% and >= 99%, and the strategic expansion index at which >= 90% was first reached;
- flow: `guidedAdmitted`, `guidedPendingRemovedByExpansion`, `guidedPendingRemovedByDrop`.

  > Deliberately **not** called `GUIDED_HEAP_EXPANDED`: a guided-admitted node can be served through the neutral lane, so the counter records removal from the pending pool by expansion, not selection from the guided heap. This is also why the counter was placed at the same site as `noteGuidedRemoved()` rather than at the heap pop.
- two composition snapshots of the **live rank-10** pool (first trim at >= 99% rank-10 saturation, and end of run): `liveGuidedCount`, `distinctSemanticIdentities`, `distinctStructuralKeys`, `topSemanticIdentityMultiplicities`, `byActionKind`, `byFloor`, `multiVariantStructuralGroupCount`, `maxVariantsPerStructuralGroup`, and the within-group Pareto composition.

  > The within-group composition uses an exact sorted incremental frontier sweep, not pairwise comparison, so a group with hundreds of variants stays cheap, and it never writes `node.rankValue` or `node.rank20ParetoDominated` (which the trim later reads). Equal resource vectors do not dominate each other - `paretoDominates` requires a strict improvement.

### 2.2 Preflight: the telemetry is read-only

A 300-expansion, cap-8 preflight (small cap so trims actually occur) runs twice, flag off and flag on, and compares every result field except the telemetry payload, wall time, and RSS:

```ini
TELEMETRY_IS_READ_ONLY = TRUE      (differing search fields: none)
TELEMETRY_OBSERVED_TRIMS_IN_PREFLIGHT = TRUE
```

This is the durable evidence for `SEARCH_POLICY_CHANGE = NONE`. Note that at cap 1024 the pool does not fill within 400 expansions, which is why the preflight uses a small cap to exercise the trim path.

## 4. What this answers

**Q1 - Is the all-rank-10 pool a baseline property or a stable-tie-break property?**

```ini
STABLE_RANK10_SATURATION_GT_LEGACY = TRUE
  occupancy mean         0.591 vs 0.010   (59x)
  trims at >= 99% cap    2779  vs 0
  final kept rank10      1024  vs 40   of 1024
  live guided at end     1023  vs 38
SATURATION_IS_NOT_A_BASELINE_PROPERTY = ESTABLISHED_AT_FIXED_WORK_8000
PR_5_26G_SATURATION_OBSERVATION = TRUE_FOR_THE_STABLE_CONFIGURATION_MEASURED_IN_BOTH_5_26G_ARMS
```

This is the round's main result and it reframes 5.26g. The 5.26g A/B deliberately ran `stableGuidedTieBreak` ON in both arms (the repair was measured on top of the configuration that exposed the memory problem), so its "1018-1022 of 1024, demotion changes who not how many" observation was measured entirely inside the stable regime. The baseline does **not** have this property: with `stableGuidedTieBreak` OFF the pool holds mostly rank-20/rank-30 work (mean rank-10 occupancy 1.0%, 840 rank-20 and 144 rank-30 slots at the final trim) and never drops a single guided node.

**Q2 - What is in the approximately 1020 slots?**

```ini
GUIDED_VARIANT_MULTIPLICITY = ESTABLISHED
  13 distinct semantic identities -> 1023 live guided slots at END
  one identity holds 233 slots; max variants within one structural group = 135
GUIDED_POOL_IS_ENTIRELY_SHALLOW = TRUE   (byFloor: MT2 908 / MT1 115, zero MT3/MT4)
```

Both halves of the owner's dichotomy are present at once, and they are the same phenomenon: a *few* strategic identities, each exploded into *many* structural/resource variants. So the blocker class is variant multiplicity - but note the second axis, because it may matter more than the multiplicity: **the guided pool contains no MT3 or MT4 work at all**, at either snapshot. `identityInFrontier` in this window is entirely a set of MT1/MT2 actions.

**Q3 - Why is the pool persistently near-fully rank-10?**

```ini
GUIDED_FLOW_IMBALANCE = DIRECTLY_ESTABLISHED_FOR_THE_STABLE_ARM
ADMISSIONS_EXCEED_REMOVALS_PER_EXPANSION = TRUE (+0.128 / expansion)
DOMINANT_TERM = TRAFFIC_LEVEL (admissions 0.501 -> 1.481 per expansion, 2.95x)
RANK10_DROP_IS_TOO_SMALL = FALSE
  (stable removes 6294 guided nodes by drop = 0.787 / expansion; legacy removes 0)
```

Of the owner's three candidate causes, **`rank10 drop 太少` is falsified**: guided drops are not rare in the stable arm, they are massive. The cause is flow *level*: the stable arm admits ~2.95x more guided work per expansion than legacy, and it removes only ~91% of it, so the ~9% excess accumulates into a pool that rank-10 always wins. It is worth being precise here, because "admissions ≫ removals" is not what the numbers say - the ratio is 1.094, not lopsided. What is 3x different is the **volume of guided traffic**, and the small persistent excess is enough to saturate a capped pool.

**Q4 - Is guided work dominated within its own structural group?**

```ini
LIVE_GUIDED_PARETO_DOMINATED_WITHIN_STRUCTURAL_GROUP = 868 / 1023 (84.8%) at END
                                                        662 / 1014 (65.3%) at first 99%
LIVE_GUIDED_PARETO_NONDOMINATED                        = 155 / 1023 at END
LEGACY equivalent                                      =   1 /   38 (2.6%)
```

Descriptive only - no pruning was performed and none is proposed on this basis. But it is a sharp reading: the stable arm's capped pool is ~85% dominated duplicates, while the legacy pool is essentially a nondominated frontier (1 dominated out of 38). The stable service order does not merely admit more guided work; it fills the cap with strictly worse copies of a handful of actions.

### 4.1 One adjacent observation about the two removal channels

`removed by drop` and `removed by expansion` behave very differently in memory terms. `lib/transport-collapse.js` has exactly **one** state-release site - the end of the expansion block (`node.closed = true; node.state = null;`). A **dropped** node is not released: it leaves `pending` but its state stays reachable through `nodesById`. So of the stable arm's 10824 guided removals, the 6294 dropped ones do not reclaim memory, and RSS at matched work scales with 2.95x more guided *traffic* rather than with pool size. This is recorded as an observation from reading the code, **not** as a proposed change; nothing was modified.

Scope limits, stated rather than implied:

- This is a **fixed-work 8000-expansion** diagnostic on one region (MT1..MT4, goal MT4, chaos MT1). The saturation comparison is established *at this window*, not as a general law of the search.
- The depth difference (26 vs 22) is reported but no capability reading is made from it - this round has no capability gate and reads no oracle key.
- Composition classes (`GUIDED_VARIANT_MULTIPLICITY` etc.) are **pre-declared mechanical thresholds on measured counts**, not verdicts: `variantMultiplicityRatio >= 10` and `distinctSemanticIdentities >= cap/2` were fixed in the audit script before the run.
- `stableGuidedTieBreak` remains **opt-in, default OFF**. Nothing was promoted, and no follow-on mechanism is authorized.

## 6. Where this points (owner decision tree, for reference only)

The owner pre-declared three branches. The measured data lands on the first, with a second axis that the pre-declared branches did not anticipate:

1. `STABLE_RANK10_SATURATION >> LEGACY_RANK10_SATURATION` - **TRUE** (0.591 vs 0.010 mean, 1024 vs 40 final rank-10 slots). The owner's pre-declared reading of this branch is that the 5.26f cost is not a peripheral bug but a core search-dynamics side effect of the stable service order itself, and that `STABLE_GUIDED_TIE_BREAK = MECHANISM_POSITIVE BUT_NOT_A_GOOD_ACTIVE_POLICY` becomes the more likely ruling. That ruling is the owner's; this document supplies the numbers only.
2. Composition: `BLOCKER = GUIDED_VARIANT_MULTIPLICITY` (13 identities -> 1023 slots, one identity at 233 slots, max 135 variants per structural group). Combined with 84.8% within-group dominance, this is the branch where "guided active archive / group diversity" becomes discussable - and explicitly **not** a fixed quota or reserve.
3. Flow: `GUIDED_FLOW_IMBALANCE = DIRECTLY_ESTABLISHED`, driven by traffic level (2.95x) rather than by lopsided removal.

Plus one axis the pre-declared branches did not cover, which may be the more important one: the guided pool is **100% MT1/MT2**. Whatever is decided about variant multiplicity, the frontier-guidance set in this window contains no MT3/MT4 identity at all.
