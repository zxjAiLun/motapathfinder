## 本轮范围（observation-only）

在 5.19q/r 同一 frozen A/B（`--qualification-1000 --residual-recovery --second-residual-recovery`）上增加只读归因：

- 8 个 charged calls 的直方图：
  - hierarchyLevel = 0（root）
  - hierarchyLevel = 1（continuation-derived child）
  - hierarchyLevel >= 2
- 每层分类 useful / wasted：
  - useful = satisfied（含 materialized/finalCreated/reachedNewBest）
  - wasted = not-satisfied（含 stoppedReason 分布）
- 每层成本与 ROI（观察值，非硬阈值）：
  - expansions、chainActions、satisfiedPerCall、expansionsPerSatisfied、reachedNewBestPerSatisfied
- 未 charged 的尝试：
  - root deferred for hierarchy
  - root compiled-but-not-selected：cap-blocked / outstanding-blocked / dedup-rejected
  - continuation scheduling blocks：call-cap-exhausted / outstanding-barrier / attempt-deduplicated
  - rejected queued work（lazyWork，battle-access-*）
- 不预设“child=3 一定浪费”或“增加 child allocation 一定有效”。

### P1 修正：notSatisfied ≠ wasted

5.19s 初版把 `useful=satisfied / wasted=notSatisfied` 并把 `satisfiedPerCall` 称为 ROI。Reviewer 指出（P1）：从 5.19l 起 connector `not-satisfied / budget-exhausted` 仍可产生 witness graph → strict replay → discrete materialization → continuation progression（O1→O4 整条机制的基础）。因此 level-2+ `satisfied=0/2` 只能解释为 direct connector satisfaction=0/2，不能解释为 useful=0 / wasted=2 / ROI=0。

Repair 1（Derived-Progress-Aware Call Attribution，commit `515b112`）：以 `attemptId` 为主键，把 `survivalOpportunityWitnesses.originFailedAttemptId` 与 `survivalOpportunityResidualRecoveries.originFailedAttemptId` 回绑到原 call；每个 call 输出 `connectorOutcome` / `derivedProgress` / `productive`；per-level 聚合 failedWithRecoveredProgress / failedWithoutRecoveredProgress；指标分离为 `directConnectorSatisfactionRate` 与 `productiveCallRate`，不再单独称 ROI。

### Repair 1 conclusions（observation，非 allocation 主张）

```text
1. 固定 child=3 是否浪费？ 不能按 connector terminal status 判定。
   level-2+ 的两个 failed call 恰是 paid-witness recovery 的来源：
   cb70ef61 → O1 skeletonKing materialized
   e9c03049 → O2 devilWarrior materialized + O3/O4 residual materialized

2. 哪级 ROI 更高？ 直接 satisfaction 排序 ≠ productive 排序：
   direct:  level 1 (1.0) > level 0 (0.2) > level 2+ (0.0)
   productive: level 1 = level 2+ (1.0) > level 0 (0.2)
   level-1 ≫ root ≫ level-2+ 的直观排序被推翻

3. 是否存在 call starvation？ 仍成立（不受本 P1 影响）：
   continuation next prerequisite compiled → call-cap-exhausted（5.19m/5.19r 独立支持）
```

Caveat: `productiveCallRate` 是 frozen run 的直方图事实；它表明 failed deep calls 产生 recovered progress，但不证明调整 call 分配会改善终点 outcome。任何 allocation 修改仍需另行授权。
