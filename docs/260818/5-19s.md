## 授权与已有证据

PR-5.19m Case A 与 PR-5.19r O4 Case A 都把阻塞边界收敛到同一抽象：

```text
hierarchical prerequisite depth > available connector call budget
```

5.19r 确认 continuation/anchor/parent-floor/prerequisite 编译全链路健康；剩余问题只剩 execution capacity。因此本轮只回答 call 被谁消耗，不改 allocation。

## 本轮范围（observation-only）

在 5.19q/r 同一 frozen A/B（`--qualification-1000 --residual-recovery --second-residual-recovery`）上增加只读归因：

- 8 个 charged calls 的直方图：
  - hierarchyLevel = 0（root）
  - hierarchyLevel = 1（continuation-derived child）
  - hierarchyLevel >= 2
- 每层分类 useful / wasted：
  - useful = satisfied（含 materialized/finalCreated/reachedNewBest）
  - wasted = not-satisfied（含 stoppedReason 分布）
- 每层成本与 ROI（观察值，非硬阈值）：
  - expansions、chainActions、satisfiedPerCall、expansionsPerSatisfied、reachedNewBestPerSatisfied
- 未 charged 的尝试：
  - root deferred for hierarchy
  - root compiled-but-not-selected：cap-blocked / outstanding-blocked / dedup-rejected
  - continuation scheduling blocks：call-cap-exhausted / outstanding-barrier / attempt-deduplicated
  - rejected queued work（lazyWork，battle-access-*）
- 不预设“child=3 一定浪费”或“增加 child allocation 一定有效”。

## Synthetic gates

- 归因只在 flag on 时写入；off 时 `hierarchyCallAllocationAttribution` 为 null。
- byLevel 桶覆盖 level 0、1、>=2（若真实 run 无 level>=2 则如实为空，不伪造）。
- 计数与 witness/统计主字段一致（charged total == battleAccessPrerequisiteCalls）。
- observation 不改变任何 outcome/verdict 字段。

## Verified Result

```text
HIERARCHY_CALL_ALLOCATION_ATTRIBUTED

8 charged calls:
  level 0 (root):     5 calls, 1 satisfied (4 budget-exhausted), 206 exp/satisfied
  level 1 (child):    1 call, 1 satisfied, 9 exp/satisfied
  level 2+ (deep):    2 calls, 0 satisfied (2 budget-exhausted), 100 exp

observations (not causal allocation claims):
  root-level calls are the least efficient in this run:
    80% fail, 206 expansions per satisfied root call
  level-1 is the only 1.0 satisfiedPerCall bucket and the cheapest
  level-2+ consumed 100 expansions without satisfaction
  root-level compile-select funnel saturated: 166 cap-blocked, 56 hierarchy-deferred
```

Caveat: `satisfiedPerCall` / `expansionsPerSatisfied` are histogram facts of this frozen run, not proof that reallocating calls would improve outcome. No allocation change was made; this evidence exists to decide whether allocation changes are even worth discussing.
