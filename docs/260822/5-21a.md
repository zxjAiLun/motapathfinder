### P2-3：两种 route 口径 + 难度证据

原文档把 compact recorded artifact 的 14 条当成执行步数。两者是不同的东西，现在并列上报并交叉校验：

```text
recorded artifact   = 搜索存在 goal state 上的紧凑记录
                      = 初始 auto 前缀 + 每个 decision 一条
                      本例 14 = 4 auto 前缀 + 10 decision

runtime transcript  = storeRoute:true 重放时 runtime 真正执行的全部步骤
                      = 每个 decision + 它触发的每个 auto pickup/battle
                      本例 50 = 10 decision + 40 auto（28 pickup + 12 battle）
```

新增断言：

```text
searchRawRouteLength === replayRawRouteLength === replayState.route.length   （50）
search/replay 的 decisionDepth、autoStepCount、autoPickupCount、autoBattleCount 全等
recorded artifact 的 decision summary 序列 === replay transcript 去掉 auto: 后的序列
recorded artifact 的初始 auto 前缀 === replay transcript 的同长度前缀
```

重放改为 `storeRoute:true`，且**只对最终候选执行一次**完整重放。未修改 dp-search 让 frontier state 保存完整 route。

难度证据：新增 `difficultySnapshot`，把 I581 / I582 / `flag:level0` 归一化为数字，要求 search initial、search final、replay final 三处完全一致。本 corpus 冻结为 Chaos 表示：

```text
{"I581":0,"I582":0,"flag:level0":0}   三处完全相同
```

### 一处未能满足的子要求（需复核者裁定）

要求"resolveRecordedAction 的 fingerprintMatches=true，且 fingerprintMatchedDecisionCount === decisionsReplayed"**无法在本轮允许的文件范围内满足**。原因是两个 fingerprint 生产者格式不同：

```text
recorded（搜索记录）    battle|MT1|8|7|blackSlime        changeFloor|changeFloor@MT1:6,0
resolver（normalizeAction） battle|MT1|8,7|blackSlime     changeFloor|MT1|6,0|:next|,
```

坐标分隔符不同（`|` vs `,`），changeFloor 的结构也不同。因此 `fingerprintMatches` 对真实路线结构性地永远为 false。要对齐必须改 `route-store` 或 `simulator`，二者都不在本轮允许清单内，我也不愿意为了让断言变绿去反向拼凑格式。

处理方式：

```text
保留    每个 recorded decision 必须带非空 fingerprint（可满足，已断言）
上报    fingerprintMatchedDecisionCount = 0
        fingerprintFormatReconciled = false        ← 显式标记未对齐，不掩盖
改为断言 每个 decision 必须在 identity grade 上匹配：
        postExactState / postDominanceKey / fingerprint / path / target-stance-direction
        显式排除 summary 与 kind —— 即"禁止仅凭 summary 字符串执行"的实质要求
        本例实测 decisionMatchTypeCounts = {"path": 10}，identityGraded = 10 = decisionsReplayed
```

端到端上还有更强的三重约束共同成立：decision summary 序列逐项相等、raw route length 与四项 accounting 全等、`exactStateKey` 相同。我认为这套组合比逐步 fingerprint 相等更强，但它确实不是要求的字面形式，需要你裁定是否接受，或另行授权修改 fingerprint 生产者。

五次独立运行的实测分布：

```text
binding=rss   expansions=849    wall=8753ms    rss=256.9MB
binding=rss   expansions=1214   wall=12763ms   rss=256.3MB
binding=rss   expansions=2127   wall=23627ms   rss=256.5MB

binding=wall  expansions=2706   wall=30011ms   rss=248.0MB
```

**关键事实：expansion cap 从来不是瓶颈。** 上限 50000，实测只用到 849–2706 就因内存或时间触顶。所以"把 maxExpandedStates 提高"不会有任何帮助 —— 本轮也不授权提高。checker 因此冻结的是 `bindingConstraint ∈ {rss, wall}` 与 `expansions < cap/10`，而不是某个具体数字。

### 这个失败说明什么

```text
说明   MT1→MT2（24 expansions）与 MT1→MT6 之间不是线性差距。
       同一套 DP、同一套 runtime、同一预算，目标从 MT2 推到 MT6 之后，
       搜索在只到达 MT2 的深度上就耗尽了 256MB / 30s。
       瓶颈是 per-state 内存与单状态展开成本，不是展开次数。

不说明 MT6 不可达。只说明在当前预算与当前状态表示下不可达。
不说明 5.20a–c 的静态 core/adapter 能改善这一点——它们没有参与任何一次真实路线，
       本轮起标记为 EXPERIMENTAL_FROZEN / REGRESSION_ONLY，不再作为 production promotion 路径。
```

按授权，本轮不提高 cap、不修改 `searchDP` / `simulator` / battle / event runtime、不追加归因字段，也不开归因小轮。真实结果已冻结，实现到此结束。
