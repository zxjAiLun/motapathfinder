## Phases

### Phase 1 - oracle to current exact-state checkpoints

Replay `routes/fixtures/mt1-mt4-hp6428-best.route.json` (55 decisions; known to execute to MT4 on the current simulator) from the canonical CHAOS MT1 initial state through the same `resolveRecordedAction()` the strict gate uses. Per step record: step index, floorId, action kind/summary, pre/post exact key via the CURRENT `buildStateKey()`, floor change, and `transportSignature(pre) === transportSignature(post)`.

Two sequences:

```text
ALL_ORACLE_STEPS               all replayed steps
STRATEGIC_ORACLE_CHECKPOINTS   only steps whose transport signature changed
```

The strategic checkpoints are the primary sequence for lifecycle comparison: search-level nodes are strategic successors; transport-only steps may only ever appear inside local closures (tracked as `closureSeen`).

The fixture's stored stateKey strings use an older projected format and are NOT used; keys are regenerated from replayed states.

### Phase 2 - observational lifecycle hook only

`transport-collapse.search()` gains an optional `onCandidateLifecycle(event)` callback:

- Return values are completely ignored; the search never reads anything from the observer.
- The hook is null-guarded: absent callback = zero behavior and (barring one truthiness test) zero cost.
- Observer exceptions propagate (a broken recorder fails loudly); they can abort the diagnostic run but cannot steer any decision.
- Events: `closureSeen` (exactKey), `strategicGenerated` (exactKey, kind), `duplicateSkipped` (exactKey, kind), `registered` (exactKey, depth, floorId), `classified` (exactKey, identity, kind, frontierGuided, guidedAdmitted, skylineDominated, depth, floorId, plus a small hero resource snapshot for arrival-state quality analysis), `dropped` (exactKey, rankClass, kind, frontierGuided, guidedAdmitted, skylineDominated), `expanded` (exactKey, depth, floorId), `goal` (exactKey).
- The audit harness filters events OUTSIDE the search, by oracle exact keys. `ORACLE_KEYS_AFFECT_SEARCH_DECISIONS = FALSE`.
- A permanent micro proves callback inertness: the retention-contract stub scenario run with a junk-returning observer must produce results identical to the unobserved run.

Stage precedence note: a `duplicateSkipped` event only means the state was already registered through another action variant; checkpoint #8's registered twin itself emitted a `dropped` event, so the real loss stage is the cap drop, not the dedup (the audit classifies dropped > duplicate for exactly this reason).

What actually happened at checkpoint #8:

```text
the oracle's skeletonWarrior state WAS generated and registered - via a twin
action variant (same battle identity, different walk path) - and that twin was
a NEUTRAL candidate: frontierGuided=false, guidedAdmitted=false,
skylineDominated=false. When the cap=1024 pool filled, the neutral twin was
dropped and never expanded. Everything downstream (43 checkpoints, including
the MT1->MT2 transition and all MT3/MT4 content) was never generated.
```

## Findings and boundaries

- **Branch A confirmed for the FIRST loss, with a twist.** The blocker is cap retention of a neutral candidate - but NOT a skyline-dominated guided one. `battle:MT1:2,1:skeletonWarrior` is in NEITHER the MT3 nor the MT4 frontier (it was already NEITHER in the PR-5.25p Diagnostic 1 winner-membership data). The known MT4 route's 9th strategic decision is a battle the autonomous frontier does not consider a prerequisite.

```ini
FIRST_LOSS_BRANCH = A_CAP_RETENTION
ITEM_POI_AS_FIRST_LOSS = FALSE
ARRIVAL_QUALITY_AS_FIRST_LOSS = FALSE
SECONDARY_MT4_BLOCKERS_AFTER_FIXING_FIRST_LOSS = UNKNOWN
```

The branch exclusions apply ONLY to the first loss. Once checkpoint #8 dies, the downstream oracle prefix never gets a chance to be tested - the 43 `NEVER_GENERATED` checkpoints are largely the mechanical consequence of the first chain break, so nothing in this audit establishes or excludes item-wiring or MT3-arrival-quality as SECONDARY blockers.

- **The MT3 winner route crosses the same state** (its step 4 is the same battle). The MT3 task survives because in the MT3-region run the neutral prefix stayed inside the cap long enough to be expanded; the MT4 run's larger guided flow crowded it out. This is a plausible reading of the two runs' drop dynamics, not an isolated proof.
- **The overlap ratio is diagnostic scale only.** 82 oracle-matched events out of 178,995 total lifecycle events describes the artifact; it is NOT a trajectory-similarity metric - once the 9th strategic prefix is dropped, the exact-state chains should not coincide, so the low overlap is largely the mechanical consequence of the first break.

```ini
ORACLE_MATCHED_LIFECYCLE_EVENTS = 82
TOTAL_LIFECYCLE_EVENTS = 178995
INTERPRETATION = DIAGNOSTIC_SCALE_ONLY / NOT_A_TRAJECTORY_SIMILARITY_METRIC
```

- **Frontier coverage limitation observed, not a proven bug.** `buildDependencyFrontier()` is explicitly a BOUNDED alternative-dependency-path construction, and `distinctAlternativePaths()` explores alternatives by banning first-path blockers/edges, with enemies costed as high-value unresolved POIs - it finds topology-reachable paths and their blockers; it does not attempt to enumerate "would fighting this non-blocking enemy early be worth it". So the observation is exactly:

```ini
FRONTIER_COVERAGE_LIMITATION = OBSERVED
FRONTIER_BUG = NOT_ESTABLISHED
```

Repairing the frontier to include this battle BECAUSE the oracle fights it would approach witness leakage and is explicitly not done.
- Not branch C or D for the first loss: the state was dropped, not merely unscheduled; and the search did reach MT3 through its own states (1,253 classified MT3-arrival states were sampled into the artifact for any future arrival-quality analysis - not analyzed this round, and they do not exclude MT3-arrival quality as a SECONDARY blocker).
- Single instrumented run; expansion/wall figures are indicative only (hook overhead + machine variance). The survival analysis itself is deterministic given the recorded events.
