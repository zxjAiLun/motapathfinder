## The implementation finding (code-level, from owner review)

`pendingRank()` (transport-collapse.js) assigns retention rank:

```text
goal state                  -> 0
node.frontierGuided         -> 10
node.paretoAdmitted         -> 20   (documented tier)
everything else             -> 30
```

But `paretoAdmitted` is only ever assigned INSIDE the `frontierSet.has(identity)` branch, so `paretoAdmitted => frontierGuided` and the rank-20 tier is **unreachable**. The documented four-tier retention (goal -> frontier guided -> Pareto admission -> insertion) is in fact three tiers (goal -> ALL frontier matches -> everything else).

Worse: a frontier-matched child that the resource skyline DOMINATES never enters the guided heap (the scheduler correctly treats it as neutral), but it still carries `frontierGuided = true`, so cap retention keeps it as a rank-10 VIP. This contradicts the PR-5.25n intent: only Pareto-nondominated frontier nodes are guided; dominated ones are neutral only.

Relevance to the 5.25q/5.25r MT3 misses: after the changeFloor identity repair, one real run generated 1,844 guided changeFloor children. How many of those are skyline-dominated is unmeasured (no counter exists). The plausible mechanism - corrected identities flooding the rank-10 retention class with dominated corridor/revisit variants that crowd out other resource-state prefixes until the admitted space exhausts on wrong combinations - is a high-priority candidate explanation, not yet a proven root cause.

## Term contract (locked)

```text
frontierGuided = ACTION_SEMANTIC_IDENTITY_IS_IN_AUTONOMOUS_FRONTIER   (structural classification)
guidedAdmitted = FRONTIER_GUIDED
                 AND PASSED_CURRENT_RESOURCE_SKYLINE_ADMISSION
                 AND WAS_INSERTED_INTO_THE_GUIDED_HEAP                (scheduling eligibility)

CAP_RETENTION = GOAL > ACTUALLY_GUIDED_ADMITTED > NEUTRAL
```

With `resourceSkylinePriority` disabled, every frontier match is heap-pushed, so `guidedAdmitted == frontierGuided` and non-skyline configurations (e.g. the 5.25m dual queue) keep their exact prior behavior.

- A PHASE_3 MISS with `SEARCH_COMPLETE = TRUE` again would mean the aligned retention still excludes the winning prefix; the 5.25T survival audit (winner route as read-only oracle, passively recording `SEEN_IN_TRANSPORT_CLOSURE / STRATEGIC_SUCCESSOR_GENERATED / REGISTERED / FRONTIER_GUIDED / GUIDED_ADMITTED / DROPPED_BY_CAP / EXPANDED` per winner postExactStateKey) is then the designated next round.

Wiring auto-effect prerequisites into the candidate representation is a candidate FOLLOW-UP layer, explicitly not this round.
