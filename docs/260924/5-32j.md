## 2026-09-24 接手更正（当前有效口径）

本次只核对既有测量，不增加性能实验。下方“测量结果与瓶颈画像”保留初稿历史，但以下纠正优先：

- 39.0% `structuredClone` / 5.0% GC 来自 **seed/P42/incumbent 三固定状态重复微测＋启动**的 3,706 个样本，不是实际 32k 搜索 CPU 分布。完整 search wall 热点占比仍未知。
- 三个固定状态各枚举 4/4/7 个动作，不能据此认定全搜索分支因子，也不能计算真实搜索的“10x 仅多 1.7 步”。图搜索、去重、支配与多根前沿不满足该满树模型。
- **撤回 Rust 4x–10x 估值**。未实现 Rust 对照；COW/紧凑状态也并非只能用 Rust，Rust 不自动消除复制成本。实际收益未知。
- **撤回“数十万展开必耗尽 6GB/8GB”及几小时必停止的断言**。32k 单点内存不能预测长期增长；现有资料不足以给出 OOM 展开数或持续时间。无界运行仍未授权，但原因不能伪装成已测出的内存极限。
- 32k wall/expansion、前沿和键计数属于实际搜索测量；局部 `safetyProbe`/`hazardScan` 计时可能嵌套，不是完整 wall 分解。算力、状态表示和搜索覆盖的相对瓶颈尚未量化；本轮支持“不承诺全面重写收益”，不支持“Rust一定不能解决路线”。

## 测量结果与瓶颈画像（初稿历史；不支持的外推已由上节撤回）

从历史多次 32k Control 报告及离线 CPU Profile (`CPU.20260923.171042.132813.0.001.cpuprofile`，3706 样本) 分析：

1. **JS 吞吐与内存**：
   - 32k 搜索时展开吞吐约为 **98–101 expansions/s**（每次展开约 10ms）。
   - 32k 展开后前沿约 44,885 节点，保留 29,681 个 DP key，峰值 RSS 约 1.5–2.3GB，堆内存 1.3–2.1GB。
   - 现有限额是 6GB 堆 / 8GB RSS。若无前沿压缩或磁盘换出，持续盲目搜索几小时（数十万展开）就会触发内存上限被终止，**无法直接在服务器上无损挂几天**。

2. **CPU 热点分析**：
   - **`structuredClone`（深拷贝）** 占 CPU 采样的 **39.0%**（1447/3706）。每次尝试动作和状态复制都需要大量分配与深拷贝。
   - **GC（垃圾回收）** 占约 **5.0%**（184 采样）。
   - 状态查询与瓦片读取（`getTileDefinitionByNumber`、`getTileNumberAt`）占约 16.6%。
   - `buildDpStateKey` 与 `buildFastBattleEstimateKey` 占约 7.1%。

3. **对“改成 Rust 能否提速与解决问题”的客观评估**：
   - **能提速多少？** 将状态树改为栈上不可变结构或 COW（Copy-On-Write）无 GC 结构，Rust 可以彻底消除 `structuredClone` 和 GC，纯单步模拟吞吐预估可达 **4x–10x**（达到 400–1000 eps）。
   - **能否解决路线问题？** **不能。** 魔塔分支因子约为 4–7。吞吐哪怕提升 10 倍，在指数爆炸下能多探索的深度只有 $\log_4(10) \approx 1.66$ 步。如果不把关键门打开或拿到关键道具，纯算力很快就会被 TS11–TS13 浩瀚的无关状态淹没。
   - **重写风险**：魔塔包含大量的 JS 事件解释（`project/events.js`、`afterOpenDoor`、`commonEvent`、`itemEffect`），全盘用 Rust 重写极易导致细微语义偏差，从而导致搜索出的路线无法在真实 h5 引擎中 strict replay。
   - **结论**：当前第一瓶颈是**搜索方向与目标约束（例如是否需要开绿门）**，而非纯算力。不建议开展全盘 Rust 重写。
