# PR-5.27a — Route-Free Dependency Feedback Search

Round began 2026-09-15. Baseline at round start: `dev == origin/dev`, `HEAD = 7f016ee`.

Owner authorized this as the **new mainline** after closing the PR-5.25o→5.26k flat-pool branch. The structural
reason, recorded at authorization: a single 1024-slot active pool was being asked to hold current executable actions,
future resource investment, guided prerequisites, alternative world states and branches to revisit later all at once,
so each retention repair merely moved the bottleneck. The instruction was therefore to change the *form* of the
search, not to add another retention layer:

> "根据当前失败/依赖关系，只展开一个 bounded local prerequisite；失败后自动换 checkpoint / alternative。"

```ini
ROUND       = PR-5.27a
KIND        = ROUTE_FREE_DEPENDENCY_FEEDBACK_SEARCH
TRANSPORT_COLLAPSE = NOT_TOUCHED_THIS_ROUND
NEW_API     = runDependencyFeedbackLoop (lib/dependency-feedback-controller.js)
```

## 1. What was actually missing

The repository already had the parts, which is why the round was scoped to one core change rather than a new planner:

```ini
automatic-dependency-planner.js   derives topology alternatives + prerequisites from project + current state + terminal goal
dependency-feedback-controller.js re-builds dependency context per checkpoint, skips attempted experiment keys,
                                  chooses another checkpoint/alternative, invokes the next local execution
local-dependency-executor.js      solves one local prerequisite with goal-directed searchSegmentDP(),
                                  then strict-replays the resulting checkpoints
```

What did not exist was the **loop**: a global budget, a dedup ledger and a termination condition tying those three
together. `runDependencyFeedback` was one step; nothing drove it repeatedly and nothing remembered what it had tried.

## 2. The loop contract

```text
initial exact state + one terminal goal
        |
        v
build automatic dependency context        (round 0, from the initial state alone)
        |
        v
execute one bounded local prerequisite
        |
        v
strict-replay candidate checkpoints
        |
        v
terminal reached?  --YES--> return route
        |NO
        v
feedback chooses checkpoint / alternative
        |
        v
mark experimentKey attempted
        |
        v
next bounded local execution  -->  ...
        |
        v
budget exhausted --> UNKNOWN
```

Globally maintained, and reported in `globalState`:

```ini
attemptedExperimentKeys           # burned when SELECTED, not when successful
visitedExactCheckpointStates      # exact-state fingerprints
totalLocalExpansions
roundCount
experimentKeyReuseCount           # must stay 0
repeatedCheckpointStateCount
```

The loop reads no route, no prefix, no authored milestone, no authored event order, no authored resource threshold and
no floor decomposition. `runHierarchicalBlindPlanner`'s auto-generated `auto-floor-entry-MT2/MT3/...` decomposition was
**deliberately not used**, even though it is automatic, because the product contract is now exactly
`initial state + allowed region + one terminal goal`.

Two implementation details that are contract, not incident:

- **The round-0 selection is burned too.** The initial local execution does not pass through the one-step controller,
  so its experiment identity had to be added explicitly (`stateFingerprintOf(initialState) | alternativeId |
  prerequisiteId`). Without this, round 1 can legitimately re-select the identical triple - which is precisely the
  duplication the loop exists to prevent. This was found by the Phase 1 check, not by reading the code.
- **Checkpoint ids are per-local-execution, so they collide across rounds.** `acceptedCheckpoints` therefore carries
  round-scoped labels (`round-3:checkpoint-1`); the bare `checkpoint-1` recurs every round and is not a loop-level
  identity.

One supporting fix outside the loop: `compileAutomaticFeasibilitySubgoals` dereferenced `terminalGoal.enemyId`
unconditionally, so a `floorReached` terminal goal (which has no enemy) threw
`Automatic feasibility target enemy not found: undefined`. Since the round's contract is terminal-only, it now reports
a zero baseline with `enemy: null` for `floorReached` goals and scores equipment purely by counterfactual gain. The
`bossDefeated` path is unchanged and still throws when the enemy genuinely does not exist.

## 3. Phase 1 — loop contract smoke

`check-dependency-feedback-loop.js` (`npm run check:dependency-feedback-loop`). The worlds are the **real tower
project** with only the local work budget varied (1, then 64 expansions); no fake failure is injected:

```ini
ROUTE_FREE_INPUT_CONTRACT                  = TRUE
EXPERIMENT_KEY_BURNED_ON_SELECTION         = TRUE
INITIAL_SELECTION_BURNED                   = TRUE
NO_EXPERIMENT_KEY_REUSE                    = TRUE
ACCEPTED_CHECKPOINTS_STRICT_REPLAY         = TRUE
NON_TERMINAL_STOP_ALWAYS_REPORTS_REASON    = TRUE
ALTERNATIVE_SWITCHING_OBSERVED             = TRUE
```

Observed switching on the roomier world (all keys distinct, `experimentKeyReuseCount = 0`):

```text
round 0  alternative-1 @ MT1:enemy:4,7:greenSlime    3 checkpoints   LOCAL_DEPENDENCY_MULTI_ROLE_CHECKPOINTS_VERIFIED
round 1  alternative-1 @ MT1:enemy:3,6:blackSlime    7 checkpoints   ADVANCED_TO_NEW_CHECKPOINT_STATE
round 2  alternative-5 @ MT1:enemy:3,4:slimelord     6 checkpoints   ADVANCED_TO_NEW_CHECKPOINT_STATE
round 3  alternative-5 @ MT1:enemy:8,11:bat          6 checkpoints   ADVANCED_TO_NEW_CHECKPOINT_STATE
round 4  (no remaining experiment)                                   NO_REMAINING_EXPERIMENT
```

"A non-terminal stop must always report a reason" is a real property, not decoration: the first implementation left
`terminationReason = null` whenever the *round* budget (rather than the expansion budget) was the binding one. A loop
that stops silently is worse than one that stops, so both budgets are now distinguished explicitly
(`global-round-budget-exhausted` vs `global-local-expansion-budget-exhausted`).

## 4. Phase 2 — MT1→MT3, terminal-only, route-free

```ini
GOAL               = floorReached(MT3)
INITIAL_STATE      = fresh CHAOS MT1 (no route fixture, no prefix)
MAX_ROUNDS         = 20
MAX_TOTAL_LOCAL_EXPANSIONS = 2000
LOCAL_MAX_EXPANSIONS = 200
CANDIDATE_LIMIT    = 8
MAX_RUNTIME_MS     = 0
```

Result, deterministic across repeats:

```ini
MT3_REACHED            = FALSE
VERDICT                = DEPENDENCY_FEEDBACK_LOOP_UNKNOWN_UNDER_THIS_BUDGET
TERMINATION_REASON     = no-remaining-unattempted-alternative
ROUNDS                 = 4
TOTAL_LOCAL_EXPANSIONS = 10
ATTEMPTED_KEYS         = 4
EXPERIMENT_KEY_REUSE   = 0
FINAL_FLOOR            = MT1
```

The same run with `floorReached(MT2)` gives the identical outcome (4 rounds, 10 expansions, same prerequisite ladder),
so the ceiling is not the goal's depth - it is the planner's prerequisite schedule at this state.

**The loop itself works.** It accumulates real progress rather than thrashing:

```text
atk ladder across rounds: 2 -> 6 -> 8 -> 13
round 1  MT1:enemy:3,6:blackSlime    7 checkpoints
round 2  MT1:enemy:3,4:slimelord     6 checkpoints
round 3  MT1:enemy:8,11:bat          6 checkpoints
round 4  no remaining experiment
```

Each round costs **1 expansion**: the local goal-directed search reaches its prerequisite goal immediately, so
`localMaxExpansions` is never the binding constraint (raising it from 64 to 200 changes nothing at all). The budget is
therefore not what stops this.

**What stops it** is a phase mismatch inside the dependency planner, observed directly by re-deriving the last
portfolio's evaluation:

```text
eval checkpoint-1  canAdvance=false  all-leading-prerequisites-blocked
   alternative-1  rem=4  executable=false  leading=MT2:enemy:3,4:zombie
   alternative-2  rem=4  executable=false  leading=MT2:enemy:3,4:zombie
   alternative-3  rem=4  executable=false  leading=MT2:enemy:9,4:zombieKnight
   alternative-4  rem=4  executable=false  leading=MT2:enemy:3,4:zombie
   alternative-5  rem=5  executable=false  leading=MT1:enemy:4,1:skeleton
```

Every checkpoint in the final portfolio reports `all-leading-prerequisites-blocked`. But in the *preceding* rounds the
executable leading prerequisites were **MT1** fights (`MT1:enemy:3,4:slimelord`, `MT1:enemy:8,11:bat`) while the
alternatives those prerequisites belong to are only *completed* by **MT2** transitions. Winning the MT1 fight does not
make the MT2 prerequisite `viable-at-current-state`, so the loop spends its key, improves the hero, and arrives at a
portfolio where nothing is viable - then terminates. `executeLocalDependency` only ever executes
`alternative.prerequisites[0]`, so the remaining prerequisite chain is never scheduled.

```ini
PREREQUISITE_SCHEDULING_HORIZON = LOCAL_SINGLE_PREREQUISITE
LEADING_PREREQUISITE_PROGRESS_IS_NOT_CONVERTED_INTO_NEXT_PREREQUISITE_VIABILITY = OBSERVED
LOOP_THRASHING = NOT_OBSERVED
BUDGET_WAS_THE_BINDING_CONSTRAINT = FALSE
```

## 5. Verdict and stopped work

Per the round's pre-declared gate, Phase 2 was required to be `FOUND + strict replay` and it was not:

```ini
PHASE_1 = PASS
PHASE_2_MT1_TO_MT3 = MISS
PHASE_3_MT1_TO_MT4 = NOT_RUN          (Phase 2 did not pass, so no MT4 run follows)
DIRECTION = STOP_AT_PREDECLARED_PHASE2_GATE
```

Stopping here is the authorized behaviour, not an omission. The owner's instruction was explicit that MT3 passing was
the gate for a single MT4 run and that a miss closes PR-5.27a with the dependency rounds / selected alternatives /
consumed budget recorded - which is what section 4 records.

## 6. Honest scope and non-claims

```ini
TRANSPORT_COLLAPSE_CHANGED = FALSE
PRUNING_CHANGED            = FALSE
CAP_OR_BUDGET_INCREASED    = FALSE
GUIDED_POOL_TOUCHED        = FALSE
NEW_CHECKPOINT_ARCHAEOLOGY = NONE
```

- `runDependencyFeedbackLoop` is **new API, not a new policy**: it reuses the existing one-step controller, planner,
  executor and strict replay unchanged. It adds budget, dedup and termination only.
- The loop's `routeValid` / `allAcceptedCheckpointsStrictReplay` fields are only meaningful when the terminal goal is
  reached; on a miss they are reported as `false` / vacuous rather than as failure of replay.
- `UNKNOWN_UNDER_THIS_BUDGET` is the correct label for Phase 2. This round did **not** show MT3 is unreachable by a
  dependency-feedback loop; it showed this planner/executor pairing cannot schedule past 4 rounds from CHAOS MT1.
- The Phase 2 numbers are deterministic on this machine (repeated, and identical under `MT2` and `MT3` goals), so they
  are not a machine-load artifact. They also consume so little work (10 expansions) that load could not matter.
- No claim is made that the phase mismatch is the *only* blocker; it is the first one, and it is directly observed.
