## 1. Phase 1 — static classification of the whole tracked MT4 route

Every one of the 55 tracked decisions is replayed strictly and classified with three **generic** attributes only:

```ini
FRONTIER_ELIGIBLE   semanticIdentity is in the autonomous frontierSet
COMBAT_PROGRESS     isCombatProgressTransition(preState, postState) - the same generic rule the search uses
ORDINARY_NEUTRAL    neither
```

The name is `FRONTIER_ELIGIBLE`, deliberately **not** `RANK10`: real `guidedAdmitted` also depends on runtime skyline
history, so this is an *upper bound* on rank 10, not a prediction of it.

```ini
decisions                  = 55
strategicCheckpoints       = 52
frontierSetSize            = 117
FRONTIER_ELIGIBLE          = 42
COMBAT_PROGRESS_ONLY       = 10
ORDINARY_NEUTRAL           = 0     (steps: none)
oracleReplay               = reaches MT4, final hp 6428
```

**This is the round's first answer: the invisible class is empty.** Every strategic step of the known successful
route is either frontier-eligible or caught by the generic combat-progress rule. So the strong form of "the next
blocker is a frontier coverage gap" — a class of successful steps the search cannot even classify — is not supported
by the route itself.

Two properties of this measurement matter for how far it can be pushed:

- **It is not circular.** `buildDependencyFrontier` constructs the frontier from the project and the terminal goal
  only; the witness route is opened *after* the frontier is frozen (`evaluateWitnessRecall`), so the fixture did not
  build the set it is being tested against.
- **It reproduces the historical finding rather than contradicting it.** `battle:MT1:2,1:skeletonWarrior` (decision 8,
  the first loss of the 5.25t era, then recorded as being in neither F3 nor F4) is still `FRONTIER_ELIGIBLE = FALSE`
  here - it is now `COMBAT_PROGRESS_ONLY`. That is exactly the mechanism by which the 5.25x work moved the prefix:
  the combat-progress rule covers the battles the frontier misses. The 10 combat-progress-only steps are decisions
  6-10 and the other MT1 combat steps.

The cheap question this phase was asked to answer, answered:

```ini
FRONTIER_COVERAGE_HYPOTHESIS_WEAKENED_BY_PHASE_1 = TRUE
  (ordinary neutral = 0: no strategic step is invisible to both classifiers)
```

It does **not** by itself say the search retains and serves those steps - that is Phase 2, and there the answer is
different.

The first loss, in full:

```ini
checkpoint 29
semanticIdentity  = battle:MT2:6,6:brownWizard
floor             = MT2
staticClass       = FRONTIER_ELIGIBLE      (phase 1)
frontierGuided    = TRUE
guidedAdmitted    = TRUE

                      rankClass: 10, rank20ParetoDominated: false,
                      skylineDominated: false, olderRank20PendingCount: 0 }
```

What is and is not established by these numbers:

- **Established: the first prefix loss is a rank-10 guided node that was never serviced.** It is frontier-admitted,
  combat-progress classified, and it dies without ever being expanded. The drop is not attributable to any of the
  rank-specific protections: not pure-fill-kept, not FIFO-head-displaced, not skyline-dominated (rank-10 nodes are
  not subject to the rank-20 Pareto tie-break, so `rank20ParetoDominated = false` is expected there).
- **Established: the downstream 23 `NEVER_GENERATED` checkpoints are mechanical fallout.** Checkpoint 28 (the
  predecessor) *was* expanded, so this is a genuine first loss; everything after 29 is downstream of it and must not
  be read as separate coverage evidence — which is exactly why the fate table carries
  `PREVIOUS_CHECKPOINT_EXPANDED`.
- **Established: the eviction happened in the registration window, not after a long wait.** `registeredAt = 19837`
  and the drop was observed at stamp 19836. The drop stamp is the last `expanded` event the observer had seen, so it
  is a lower bound by construction; and a trim can never precede registration. So the node existed for at most the
  next trim. Stated conservatively (owner wording, no pseudo-precise expansion number):
  `CP29_DROP = SAME_EXPANSION_END_TRIM_OR_EARLIEST_POST_REGISTRATION_TRIM`, `LONG_QUEUE_WAIT_BEFORE_DROP = FALSE`.
- **Side observation, consistent with 5.26i:** that exact key carries `registered`, `dropped` *and* `duplicateSkipped`
  events - an insert attempt after the eviction was rejected by the tombstone rather than re-entering the pool, which
  is the retained `registry.has(key)` contract working at 20k-expansion scale. (The table records flags, not
  per-event stamps, so this is an ordering-compatible reading, not a measured ordering.)

### Cross-configuration control: the same boundary, the same identity

The 5.26f survival artifact was measured with `stableGuidedTieBreak = ON` at 12024 expansions. Comparing the two:

| | 5.26f (stable ON, 12k) | 5.26j (stable OFF, 20k) |
| --- | --- | --- |
| LAST_EXPANDED_CHECKPOINT | 28 | 28 |
| FIRST_NOT_SURVIVING_CHECKPOINT | 29 | 29 |
| first-loss identity | `battle:MT2:6,6:brownWizard` | `battle:MT2:6,6:brownWizard` |
| first-loss class | rank 10, frontierGuided, guidedAdmitted | rank 10, frontierGuided, guidedAdmitted |
| FIRST_LOSS_STAGE | `KEPT_BUT_NOT_EXPANDED_BEFORE_BUDGET_END` | `DROPPED_BY_CAP` |

The boundary is identical across two different scheduler configurations and nearly two-fold different work budgets;
only the *eviction mechanism* differs (still sitting in the pool at the end of budget vs evicted by the cap). And
these are not the same search: the stable-OFF line reached 28 at 20000 expansions where the same configuration reached
13-14 around 10-11k expansions in 5.26c/5.26d, so the prefix does advance with work - it simply stops at 28 in both.
```ini
REPEATED_FIRST_LOSS_BOUNDARY_ACROSS_TWO_CONFIGURATIONS = CHECKPOINT_29
LONG_HORIZON_PLATEAU                                   = NOT_ESTABLISHED
FIRST_LOSS_CLASS                                       = RANK10_GUIDED_NOT_SERVICED
```

Owner correction (applied): `PREFIX_PLATEAU = CHECKPOINT_28` is **retracted as too strong**. The repeat of the
28/29 boundary across two configurations is real and valuable, but the same stable-OFF policy keeps advancing with
work (13/14 around 10-11k in 5.26c/5.26d, 28 at 20k), and there is no 25k/30k point on that policy, so a plateau is
not established. What survives is the class: a rank-10 guided candidate that is never serviced is the first loss on
both boundaries.

## 3. Owner pre-declared branch

```ini
BRANCH                        = J-A
first loss is rank10 guided, never expanded
```

```ini
FRONTIER_COVERAGE_BLOCKER     = NOT_SUPPORTED     (ordinal-0 invisible class, and the first loss IS frontier-admitted)
CURRENT_BLOCKER               = GUIDED_SCHEDULER_RETENTION_COUPLING
                                + LONG_HORIZON_HIGH_PRIORITY_POOL_PRESSURE
OBSERVED_FAILURE              = NEW_GUIDED_RANK10_CANDIDATE_CANNOT_ENTER_CAPPED_ACTIVE_POOL
NOT_PRIMARILY                 = GUIDED_HEAP_POP_ORDER
STABLE_FIFO                   = MASSIVELY_ACCELERATED_THE_PROBLEM
LONG_HORIZON_LEGACY_POLICY    = ALSO_REACHES_GUIDED_RETENTION_PRESSURE
```

Owner correction (applied): `CURRENT_BLOCKER = GUIDED_SERVICE / SEARCH_ORDER` is **too broad / too
scheduler-centric**. Checkpoint 29 was not "queued in the guided heap and starved"; it was `rankClass = 10` with
`pureFillKept = false`, so it lost its candidacy in the very first retention pass after registration - a rank-10
candidate competes only against goals and earlier rank-10 work. The narrower, more useful diagnosis is a
**coupling**: one attribute (`guidedAdmitted`) at once confers earlier service AND a permanent rank-10 storage
entitlement, so under long-horizon high-priority pool pressure a fresh guided candidate cannot even enter the active
pool. That reframing is why the next round is retention decoupling rather than a fourth heap-order experiment.

It also corrects the reading of 5.26h: the all-rank-10 pool should not be read as "only stable FIFO produces rank-10
accumulation". Stable FIFO massively accelerated the problem, and the long-horizon legacy policy reaches the same
pressure on its own.

Per the pre-declared tree this is the branch where the return step is **review**, not a fourth scheduler experiment:
`stableGuidedTieBreak` is already closed as `NOT_A_GOOD_ACTIVE_POLICY`, the retro demotion repair is closed negative,
and the owner's earlier ruling was explicit that guided admission-order sensitivity plus memory growth - not cp#29 -
is the real blocker. This round adds the missing identity: it is not cp#29 either, it is checkpoint 29 =
`battle:MT2:6,6:brownWizard`, a rank-10 guided node evicted unserviced in both configurations.

`branchCandidate` in the artifact is *mechanical classification of the data*; the ruling is the owner's.

## 4. Honest scope and non-claims

```ini
SEARCH_POLICY_CHANGE              = NONE
ORACLE_KEYS_AFFECT_SEARCH_DECISIONS = FALSE
NEW_PRUNING_OR_DELETION           = FALSE
CAP_OR_MEMORY_INCREASED           = FALSE
STABLE_GUIDED_TIE_BREAK_STATUS    = UNCHANGED (DEFAULT_OFF)
RETRO_DEMOTION_STATUS             = UNCHANGED (CLOSED, DEFAULT_OFF)
MT4_ROUTE_PROVEN                 = FALSE
FRONTIER_PATCH_AUTHORIZED         = FALSE
```

- One 20000-expansion run, one machine, load-dependent wall figures. `found = FALSE` here means
  `UNKNOWN_UNDER_THIS_BUDGET_AND_PRUNING_POLICY`, not a proof of impossibility.
- Phase 1 classifies the *tracked* route. It says nothing about whether other successful routes exist or about
  routes that need a step outside the frozen frontier.
- `ORDINARY_NEUTRAL = 0` weakens the frontier-coverage hypothesis; it does not disprove that the frontier set is
  incomplete in some other sense (a *different* successful route could still require a non-frontier identity).
- `FRONTIER_ELIGIBLE` is an upper bound on rank 10; a frontier-eligible identity can still be rejected at runtime by
  skyline history. Phase 2 is where that would show up, and for checkpoint 29 it did not (`guidedAdmitted = TRUE`).
- The fate table records *flags*, not per-event timestamps, so the registration/eviction window is stated as a
  construction-bounded reading rather than a measured ordering.
- No mechanism is proposed here. The 23 downstream `NEVER_GENERATED` checkpoints are fallout of one loss and are not
  evidence about frontier generation.
