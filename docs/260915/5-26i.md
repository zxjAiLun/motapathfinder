## 3. Implementation

`shared-solver/lib/transport-collapse.js`:

- `const reclaimDroppedState = config.reclaimDroppedState !== false;` — default on after Phase 2 cleared its gate,
  explicit `false` is the rollback. Mirrors the `enableMultiRootSharedDp` pattern (5.24h).
- `let droppedStatesReclaimed = 0;` and new result fields `reclaimDroppedState`, `droppedStatesReclaimed`,
  `peakHeapUsedMb` (opt-in `trackPeakHeapUsed`, `null` otherwise). `sampleRss()` now computes
  `process.memoryUsage()` once and is gated on `maxRssMb > 0 || trackPeakHeapUsed`.

Release site, placed exactly where the ordering spec requires: **after** the drop lifecycle/peer-composition events
(which read `dn.state` to build the same-identity variant view) and **after** the `noteGuidedRemoved()` guided
counter bookkeeping.

```js
if (reclaimDroppedState) {
  for (const id of droppedIds) {
    const droppedNode = nodesById.get(id);
    if (droppedNode && droppedNode.state) { droppedNode.state = null; droppedStatesReclaimed += 1; }
  }
}
```

Deliberately **not** done (V1 releases state only): `closed` is not set; `key`, `parentId`, `pendingSeq`,
`macroChain`, `macroTrace`, `semanticIdentity`, `rankValue`/rank metadata and `dropped` are kept; the registry shape
is untouched; `nodesById` keeps the entry.

Why this is safe, stated as the audit that was actually performed:

- **A dropped node can never have descendants.** Generation happens only during expansion, and an expanded node is
  `closed` and filtered out of `entries` by `!node.closed`, so it can never enter `droppedIds`. Nothing walks
  `parentId` from a dropped node.
- **The registry never reads a value's `state`.** The duplicate contract is `registry.has(candidate.key)` alone; there
  is no `registry.get()`.
- **`nodesById` is never bulk-iterated** (`.values`/`.entries`/`forEach` are absent) - only `.get`.
- Of the 34 `.state` read sites, every remaining one is `pending`-scoped (a dropped node has been spliced out of
  `pending` at the trim rebuild), null-guarded (`if (!node.state) return null`), or on the currently-expanded node.
- The 5.26g demotion sweep, the 5.26h trim telemetry, the 5.26h `buildGuidedPoolSnapshot` and the `livePendingIds`
  rebuild never read a dropped node's state.

The claim that matters is not the audit but the fixed-work A/B in section 5: byte-identical trajectory.

How each property is actually observed (not merely asserted):

- `DROP_EVENT_STILL_SEES_FULL_STATE` - every `dropped` event carries `sameIdentityPeers`, and

- `DROPPED_NODE_STATE_RELEASED_AFTER_DROP_OBSERVATION` - `droppedStatesReclaimed === candidatesDropped` in both `on`

- `FUTURE_SAME_EXACT_KEY_STILL_DUPLICATE_SKIPPED` - identical `duplicateSkipped` volume and identical `registrySize`
  across arms, with the non-vacuity guard that the fixture observes thousands of duplicate skips.
- `..._IDENTICAL_AT_FIXED_WORK` - every result field except the accounting set (`wallMs`, `peakRssMb`,
  `peakHeapUsedMb`, `droppedStatesReclaimed`, `reclaimDroppedState`, `signatureWallMs`) is compared, plus the route,
  the route trace and the whole lifecycle event stream.
- Retro fixture: demotions identical (76 = 76) and non-zero, and every result field identical apart from accounting.
  This is the case where dropped node ids stay alive in a skyline group set.

> Harness note (a real trap this round): the first version of this micro ran all four arms sequentially in one
> process. It produced **reversed** memory readings (`off` 636.4 MB vs `on` 1001.1 MB) and its fourth arm was
> terminated by the 2048 MB RSS limit, which made two assertions fail. The cause is not the mechanism:
> `maxRssMb` is process-level and V8 does not return freed heap, so each arm inherits its predecessors' footprint.
> Every arm now runs in its own child process, which is the same rule the 5.26f/g/h audits already followed. The
> earlier reversed numbers are discarded, not explained away.

Two things are worth stating carefully here.

1. **The 3.4x lift is not a controlled measurement.** `pr526f-mt4.json` is the *stable tie-break ON* arm; this run is stable OFF. The
   controlled number for reclamation's effect on memory is Phase 2 (`-457.8 MB` at matched work on an identical trajectory). The
   comparison here is a cross-configuration reference point, useful for scale, not for attribution.
2. **The frozen 180 s gate can no longer see this memory work at all.** MT4 needs ~38759 expansions to reach the RSS ceiling.
   Even at the fastest per-expansion rate measured on this machine (5.26f's stable-ON MT4: 9.1 ms/expansion) that is ~350 s of work;
   at stable-OFF rates it is 10+ minutes. So under a frozen 180 s budget MT4 is **wall-bound by construction**, and 5.26i's memory
   saving cannot move the frozen MT4 gate, no matter how effective it is. This is a property of the gate, not of the mechanism.

Consequence for the next step, recorded as an open question rather than a decision: with the memory ceiling pushed 3.4x out and the
result **still** a miss at depth 39 on MT3, `MT4_MISS = NOT_RESOURCE_CEILING_BOUND_AT_THIS_SCALE`. That is the owner's
"revisit the real capability blocker" branch, and it points at what the earlier rounds already suspected (frontier coverage /
retention of non-frontier oracle-prefix states), not at memory.

## 7. Falsification

The ordering property is the one thing this round could get silently wrong, so it was falsified by execution rather than argued.

The reclamation block was temporarily moved **before** the drop lifecycle/peer-composition loop, and the micro's `on` arm was run
with the mutation in place (`lib/transport-collapse.js` backed up to `/tmp` first, restore verified by md5
`a9e753d2c24c1bea38ccb2c3c2af9912`):

```ini
MUTATION                      = reclaim dropped state BEFORE the drop observation
runError                      = null      (it degrades silently, it does not throw)
peerPayloadCount              = 1765
peerPayloadsWithStructuralKey = 0         (was 1765 of 1765)
reclaimed / dropped           = 1765 / 1765
=> DROP_EVENT_STILL_SEES_FULL_STATE = FAIL
=> the lifecycle event stream also differs from the OFF arm, so SEARCH_RESULT_AND_ROUTE_..._IDENTICAL_AT_FIXED_WORK = FAIL
```

Two independent assertions catch the mutation, and the failure is a *test* failure with a readable label, not a crash. Restoring the
file restored all 23 assertions (the pre-mutation file hash is the one that passed section 4).
