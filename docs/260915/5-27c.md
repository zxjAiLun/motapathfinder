# PR-5.27c — Branch Lifecycle, Commitment, and Full Route Strict Replay

Round began 2026-09-15. Baseline at round start: `dev == origin/dev`, `HEAD = 7d4e22c` (PR-5.27b).

Authorized by the owner following review of PR-5.27b. Two critical P1 contract gaps in 5.27b were identified:
1. **Monotonic branch exhaustion was missing**: An immutable state's candidate experiments can only shrink as
   `attemptedExperimentKeys` grows. Thus, a branch evaluated as `canAdvance = false` can never later become viable under the
   current planner contract. Keeping all branches permanently `open` inflated the reported live branch count (e.g. 130/211
   branches were reported open when in fact ~95% were permanently blocked).
2. **True end-to-end full route strict replay verification was missing**: 5.27b verified per-segment replay flags and stitched
   route shape, but did not execute `verifyStrictReplay` on the stitched route from the original initial state.

The owner also authorized testing **Commit-on-Success, Backtrack-on-Block** (preferring newly opened child cohorts before
falling back to historical branches) while explicitly forbidding branch pruning, branch caps, or new heuristics.

## 1. Phase 0: Correctness Repairs

### 1.1 Monotonic Branch Exhaustion
In `lib/dependency-feedback-controller.js`, when a portfolio evaluation produces `canAdvance = false` for an evaluated branch,
that branch is immediately marked `status = "exhausted"` with `exhaustedReason = "all-leading-prerequisites-blocked"`.
Similarly, when a preferred child cohort is evaluated and no child can advance, the non-advancing cohort members are marked
exhausted with `exhaustedReason = "all-alternatives-blocked-in-cohort"`.
This eliminates false `open` accumulation: at 40 rounds, `openBranchCount` drops from 211 to **11** (203 branches correctly
recognized as exhausted).

### 1.2 End-to-End Full Route Strict Replay
Whenever `reachedTerminal = true`, `runDependencyFeedbackLoop` now invokes:
```js
verifyStrictReplay(replaySim, summaries, {
  initialState,
  isGoalState: (s) => terminalGoalReached(project, s, terminalGoal),
});
```
The result is exported as `result.fullRouteStrictReplay` and recorded in `result.routeProvenance.fullRouteStrictReplayValid`.
The terminal verdict requires `fullRouteStrictReplay.ok === true` in addition to per-segment replay flags.

### 1.3 Telemetry Additions
`globalState` now reports:
- `uniqueExactStateCount`: Number of distinct exact state fingerprints across all branches in the tree.
- `advanceableBranchCount`: Number of open branches evaluated as advanceable.

## 2. Mechanism: Commit-on-Success, Backtrack-on-Block

`runDependencyFeedbackLoop` maintains a `preferredCohortBranchIds` set:
1. When round 0 or a subsequent round successfully produces child checkpoints (`openedChildren.length > 0`), those child
   branch IDs become the preferred cohort.
2. In the next round, if `commitSuccessfulLineage !== false` and the preferred cohort contains open branches, the portfolio
   is restricted to the preferred cohort.
3. If any child in the cohort can advance, the planner selects from the cohort using existing `compareCheckpoint()` ranking.
4. If all children in the cohort are blocked/exhausted, they are marked exhausted, the cohort is cleared, and the planner
   falls back to the global historical open branches portfolio.

## 3. Phase 1: Synthetic Commitment and Replay Contract

commitment, fallback, and full route replay:
```text

 ├─ A (margin 700) -> A1 (margin 500) -> A2 (margin 500) -> dead end
 └─ B (margin 600) -> B1 (terminal)
```
- **Negative control (commitment OFF)**: Because margin 600 > 500, the uncommitted planner jumps immediately from `ROOT->A`

### Critical Diagnosis from Phase 2
1. **The search sequence materially changed** (27 of 41 rounds selected different branches/alternatives), and ON completed
   27.4% faster by avoiding premature global portfolio re-evaluations.
2. **Lineage depth did not advance past 5, and cumulative decision depth did not advance past 10**.
   Inspection of the deepest branches (`depth = 4..5`, `cumDec = 6..10`) reveals why:
   Once an active child reaches depth 4..5 on MT1, all its alternatives become `all-leading-prerequisites-blocked` because
   the remaining viable prerequisites belong to the **next stage (MT2)**, which the local single-prerequisite executor
   cannot schedule from MT1.
3. Under the monotonic contract, **those deep children exhaust immediately** (`all-alternatives-blocked-in-cohort`).
   The cohort blocks, commitment clears, and the planner falls back to older siblings in the global portfolio.
   The planner then tries other MT1 branches, exhausts them too, and eventually hits the 40-round ceiling.

This decisively answers the owner's sequencing question:
```ini
COMMITMENT_BEFORE_PREREQUISITE_CHAIN = COMPLETED
COMMITMENT_ALONE_SUFFICIENT_FOR_MT3 = FALSE
ISOLATED_BLOCKER = ACTIVE_LINEAGE_EXHAUSTS_AT_STAGE_BOUNDARY_REQUIRING_MULTI_PREREQUISITE_HORIZON
```
The search is **no longer falsely proliferated** (open branches are 11, not 211). It is **not thrashing or stuck in loops**.
It commits, exhaustively exhausts MT1 options, and cannot cross the MT1->MT2 boundary because the local executor cannot
span the multi-prerequisite gap to make the transition viable.
