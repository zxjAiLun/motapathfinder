`RANK20_DOMINATED_BACKLOG = ROBUSTLY_OBSERVED` is unaffected - the over-cap excess is small, the end snapshot is still 80% rank-20, and rank-30 goes from 2 to 0.

Also corrected: the `enqueued` comment claimed `guidedAdmitted/combatProgress` "are final by now". That is true for the peers read there (registered in earlier iterations) but **false for the child itself**, whose `guidedAdmitted` is assigned in the frontier branch afterwards - which is exactly why the field is named `rankClassBeforeGuidedAdmission`. Comment only, no behaviour change.

## Phase 1 - micros

`check:neutral-pareto-substitution` (`check-neutral-pareto-substitution.js`), new graded test. Stub world where every action shares one tile (identical semantic identity) and leaves `hero.loc` untouched (identical structural key), with an empty frontier set so every expansion is a neutral expansion and the expansion ORDER is directly observable.

```ini
A  late dominator  OFF -> [D1:weak, O:unrelated, L:strong]
                   ON  -> [L:strong, D1:weak, O:unrelated]
A2 dominator chain OFF -> [D1, D2, L]
                   ON  -> [L:strongest, D2:middle, D1:weakest]
B  incomparable    forward -> [A:bulk, B:power]   reverse -> [B:power, A:bulk]
C1 different identity            -> [A:small, B:huge]     (B dominates A resource-wise; NO substitution)
C2 same identity, different key  -> [A:samespot, B:moved] (NO substitution)
```

A2 is the case the owner specified: `dominators(D1) = {D2, L}`, but L dominates D2, so picking the first dominator would waste the turn exactly as picking D1 would. The mechanism takes the dominator **frontier**.

**Both non-vacuous, falsified deliberately:**

- Removing the group-key guard → C1 and C2 fail (cross-group substitution happens).
- Removing the dominator-frontier filter → A2 fails (`got "D2:middle", want "L:strongest"`).

`D1` is never deleted: it is still expanded, and `no candidate dropped at all` is asserted.

### Two observations that must not be buried

**1. The realized allocation moved, even though the rule did not.** `neutralEvery` and the due-condition are untouched, but the observed mix changed:

```ini
OFF: guided=5676 neutral=2324  (neutral share 29.05%)
ON : guided=4791 neutral=3209  (neutral share 40.1%)
```

The owner pre-registered `NEUTRAL_SHARE = UNCHANGED`. The *rule* is unchanged; the realized mix is not, because the trajectory changes and with it how often the guided heap is empty (which forces a neutral turn). This is reported, not explained away.

**2. The mechanism fires on most neutral turns.** `2343` substitutions over `3209` neutral expansions ≈ **73%**. This is not a rare correction of an occasional inversion - it is the normal operating mode of the neutral lane under this workload. The rule is narrow (one turn, same group, strict dominance only); its **frequency is not**.

**3. The way the gate passed is broader than a local reorder.** cp#9 registers at expansion 5958 in the OFF arm, yet is expanded at expansion **462** in the ON arm. It cannot have been reordered into that slot - the whole trajectory differs, so cp#9 is *generated* at a different point too. The pre-declared condition is met, but the mechanism by which it is met is a global search-order change, not merely "the head was swapped for its dominator".

## What this establishes, and what it does not

Established:

- The scheduler rule is implemented exactly as specified, and the micros pin each clause (frontier-not-first-dominator, incomparable no-op, cross-group no-op), both falsified.
- The pre-declared fixed-work condition is met: cp#9 unexpanded without the mechanism, expanded with it.
- MT3 still passes its frozen gate with strict replay.
- In the wall-limited MT4 configuration cp#9 is expanded and the first oracle loss moves from checkpoint 9 to 14.

**Not** established:

- **MT4 is still a MISS.** No capability claim.
- **No causal claim that the substitution specifically is what advances cp#14.** The trajectory changes wholesale; the honest statement is that the mechanism was enabled and the first loss moved, not that a particular local reorder caused it.
- No claim that the substitution is "narrow in effect" - see the frequency and allocation observations above.
- The audit run stopped on **RSS** (2050.1MB against the 2048MB ceiling at 164,698ms), while the actual MT4 gate run stopped on **time** (180,006ms, 8891 expansions). Those are different limits, so the two runs are not interchangeable.
- The mechanism has no ratio to tune. If the pre-declared condition had failed the instruction was STOP, not adjust; it passed, so nothing was tuned.
