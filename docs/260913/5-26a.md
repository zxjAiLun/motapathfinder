### The owner's correction, and why it changed the design

The PR-5.25z write-up suggested "extend the existing skyline screening to rank 20". The owner rejected that as insufficient, and the code confirms it: `skylineSet.query()/insert()` is **append-only prior-seen admission**. `insert()` never demotes an existing member, so a variant dominated by a *later* arrival keeps its slot. That is exactly the cp#9 case - 28 low-HP variants arrived first, then a strictly better one arrived and was overwritten by them.

```ini
EXISTING_SKYLINE_DIRECT_REUSE = INSUFFICIENT  # prior-seen admission, no retroactive demotion
```

Hence the mechanism is **trim-time reclassification over the current pending set**, which naturally lets a late strong variant overtake earlier weak ones.

## Phase 1 - micros

`check:bounded-retention-contract` extended with a purpose-built stub where every action shares one tile (one semantic identity) and leaves `hero.loc` untouched (one structural key), so the variants differ **only** in resources - the exact shape PR-5.25z found. The frontier set is empty, so all variants are rank 20 via combatProgress and none is rank 10.

**Late dominator (cap 2, generation order D1 hp100, D2 hp120, L hp200):**

```ini
dynamicDroppedL = FALSE    # the strong late variant survives
legacyDroppedL  = TRUE     # pure insertion order drops it
rescued = 1, changedTrims = 1, dropped = ["p:D2"]
```

This is the regression test for the stale-skyline defect: it fails under the pre-5.26a order and passes now.

**Incomparable trade-off (cap 1, A hp200/atk2 vs B hp100/atk5):**

```ini
dominatedPending = 0            # no scalar weighting fabricated a domination
nondominatedPending = 2
AB order drops B, BA order drops A   # insertion order decides, both ways
```

A hidden scalar preference would pick the same winner in both generation orders. It does not, so `NO_SCALAR_WEIGHTING = TRUE` is locked behaviourally.

## Phase 2 - implementation

`shared-solver/lib/transport-collapse.js`:

- Group key = `semanticIdentity + "\u0000" + buildStructuralStateKey(state)`, memoized on the node. Nodes that cannot be classified are left **unpenalized** rather than guessed at.
- `classifyRank20Pareto(entries)` runs at cap-trim time over the current pending rank-20 entries.
- Fill order becomes `rank -> (rank 20 only) nondominated before dominated -> insertion`.
- The flag is transient per trim. It is **never** written into `node.rankValue`, which is cached and would go stale as peers come and go.
- Only groups whose membership changed are re-classified, because Pareto status is **not monotone**: a node dominated only by a peer that has since been dropped becomes nondominated.

```ini
SCHEDULER_CHANGE = NONE
HARD_PRUNING = FALSE
DOMINATED_CANDIDATE_DELETED_AT_GENERATION = FALSE
RANK_PROMOTION_TO_10 = FALSE        # still a tie-break inside rank 20 only
```

### Algorithmic note

The first implementation used an O(g²) pairwise scan. Measured at fixed work this cost +31% on the MT3 goal, so it was replaced with an exact sorted incremental nondominated-frontier sweep, O(g·F):

- **Randomized equivalence:** 4000 cases, 39,278 dominated nodes, **0 mismatches**.
- **Real-data equivalence:** at 2000 fixed expansions the two implementations produced byte-identical counters (`recomputedGroups=3707 nd=67717 dom=793906 rescued=281 changedTrims=173`).

Eviction is sound because Pareto dominance is transitive; an evicted frontier member is re-marked dominated.

## Cost

At identical work the mechanism costs **+28%** (111.5s -> 142.3s per 8000 expansions). At 2000 fixed expansions the optimized sweep is within machine noise of the disabled arm. On the MT3 gate the qualifying run finished in 74.0s of the 180s budget.

This is the reason the wall-limited audit run reached fewer expansions than its legacy control: the mechanism does real work per trim (3,149 nondominated candidates rescued across 1,169 trims in the fixed-work run).

## What this establishes, and what it does not

Established:

- The rank-20 retention class, which PR-5.25z showed was competing over a handful of actions with many resource variants, now prefers the Pareto-nondominated variant within a (semantic identity, structural state key) group, and a late strong variant can overtake earlier weak ones - which the append-only skyline provably could not do.
- cp#9's exact state is generated and deduplicated in both arms; under legacy it was evicted by the cap, under the new mechanism it is retained. Verified at identical fixed work.
- MT3 still passes its frozen gate with strict replay after the change.

**Not** established:

- **MT4 is still a MISS.** No capability claim of any kind. `MT4_TRANSFER = NOT_OBSERVED_UNDER_THE_FROZEN_CAP_1024_CONFIGURATION`.
- cp#9 being "retained" means only **not dropped before the budget ended**. It was **not expanded**, and MT4 was not reached (deepest = MT3) in either arm of the fixed-work A/B. Retention is necessary, not sufficient.
- ~~The dominant limitation is now coverage: **42 of 43** non-surviving oracle checkpoints are `NEVER_GENERATED`~~ **WITHDRAWN by PR-5.26b.** The stage name above was itself a classifier bug, and the inference from the 42 does not survive it. See the correction section at the end of this document.
- The legacy arm's `CP9_DYNAMIC_PARETO_STATUS = false` is a **control artifact** (the flag is forced false when the mechanism is disabled); it is not evidence that cp#9 was Pareto-dominated.
- No hard pruning was introduced: a dominated candidate is still retained whenever capacity allows, and `dominatedKept` is nonzero on real runs.
- MT3 is one strict run, not a repeatability requalification.

## Correction appended by PR-5.26b (owner review of `9fe98c3`)

The owner approved the retention mechanism but rejected the coverage conclusion. This section is appended rather than rewritten into the text above, so the original round's reasoning stays visible.

```ini
9fe98c3 = APPROVED_WITH_REQUIRED_AUDIT_CORRECTION
PR_5_26A_MECHANISM = POSITIVE
DYNAMIC_RANK20_PARETO = KEEP
CP9_CAP_EVICTION = RESOLVED_AT_EQUAL_FIXED_WORK
"MT4_LIMITATION_IS_NOW_COVERAGE" = NOT_ESTABLISHED
```

**The error.** The survival classifier evaluated `dropped > duplicateSkipped > registered`. PR-5.25t had already established that `duplicateSkipped` is not a death event - what decides the prefix is the fate of the **canonical registered node** for the same exact key. But the precedence still let a duplicate observation outrank a **live** registered twin, so cp#9

```ini
generated = true, duplicateSkipped = true, registered = true, dropped = false, expanded = false
```

was labelled `DUPLICATE_TO_EXISTING_STATE` rather than the correct `KEPT_BUT_NOT_EXPANDED_BEFORE_BUDGET_END`. That mislabel made a retained-but-unserved node look like an upstream generation gap, which is what the coverage claim rested on.

**Corrected reading.**

```ini
CP9_SURVIVAL_STAGE = KEPT_BUT_NOT_EXPANDED_BEFORE_BUDGET_END
FIRST_CAUSAL_BOTTLENECK = CP9_REGISTERED_BUT_UNEXPANDED
DOWNSTREAM_42_NEVER_GENERATED = NOT_INDEPENDENT_BLOCKERS
GLOBAL_COVERAGE_LIMITATION = NOT_ESTABLISHED
```

The 42 downstream `NEVER_GENERATED` checkpoints remain observed, but cp#9 is the first unexpanded prefix and the oracle's next state can only appear once the previous exact state is expanded - so those 42 are plausibly the mechanical consequence of the chain breaking at cp#9, not 42 independent generation failures.

Everything else in this document stands unchanged: the mechanism, the micros, the MT3 gate, the MT4 miss, and `CP9_CAP_EVICTION = RESOLVED_AT_EQUAL_FIXED_WORK`. The fix and its consequences are in [`docs/260913/5-26b.md`](5-26b.md).
