## Phase 0 - the audit bug the owner found

`classifyStage()` in `audit-pr525t-oracle-survival.js` evaluated:

```js
dropped  >  duplicateSkipped  >  registered
```

PR-5.25t had already established that `duplicateSkipped` is **not** a death event - it only says the exact state was reached again through another action variant, and what decides the prefix is the fate of the **canonical registered node** for that key. But the precedence still let a duplicate observation outrank a **live** registered twin.

cp#9 reported exactly:

```ini
generated = true
duplicateSkipped = true
registered = true
dropped = false
expanded = false
```

a registered, retained, unexpanded node - and the classifier called it `DUPLICATE_TO_EXISTING_STATE`. That single mislabel converted "a retained node never won an expansion slot" into an apparent upstream generation gap, and that is what supported the withdrawn claim that the MT4 limitation had become coverage.

### The repair

Precedence now follows the registered node's own fate:

```text
expanded                   -> SURVIVED
dropped                    -> DROPPED_BY_CAP
registered                 -> REGISTERED_NEUTRAL_NOT_EXPANDED     (skyline dominated)
                           |  KEPT_BUT_NOT_EXPANDED_BEFORE_BUDGET_END
duplicateSkipped (no twin) -> DUPLICATE_WITHOUT_OBSERVED_REGISTERED_TWIN
otherwise                  -> NEVER_GENERATED
```

`duplicateSkipped` is demoted to the annotation `ALSO_SEEN_AS_DUPLICATE_VARIANT` and is never a loss stage on its own. The retired names `DUPLICATE_TO_EXISTING_STATE`, `KEPT_BUT_NOT_EXPANDED_BEFORE_TIMEOUT` and `REGISTERED_BUT_SKYLINE_DOMINATED` no longer appear.

### The micro that locks it

New graded test `check-oracle-survival-taxonomy.js` (`npm run check:oracle-survival-taxonomy`), a pure function of one checkpoint's event list - no search, no simulator. It asserts the exact cp#9 combination, the reversed event order, both drop orderings, skyline-dominated registration, the no-twin duplicate, and the empty/undefined/closure-only boundaries, and it fails if any retired stage name is ever returned again.

**Falsification:** restoring the old precedence was deliberately attempted and the micro failed on 4 assertions (`EXIT=1`), then the file was restored. The test is live, not vacuous.

## Phase 1 - registration-age telemetry

Generic and observational, added to `lib/transport-collapse.js`:

- `registered` lifecycle event gains `nodeId`, `pendingSeq`, `registeredAtStrategicExpansion`.
- `classified`, `expanded` and `dropped` gain the matching `nodeId`.
- The child node carries `pendingSeq` (the counter retention already used) and `registeredAtStrategicExpansion`.

None of these are read by ranking, retention, scheduling or termination; they only make a candidate's queue age observable.

### Reading the verdict

```ini
CP9_REGISTERED_AT_EXPANSION = 5958   # 74% through the run: NOT late generation
                                     # (late-generation cut = 6967)
CP9_STILL_PENDING_AT_END = TRUE      # it was never dropped - 5.26a held
CP9_NEUTRAL_DISTANCE_FROM_HEAD = 300 # 300 live candidates still ahead of it
CP9_GUIDED_ADMITTED = FALSE          # it never entered the guided heap
NEUTRAL_LANE_SHARE = 0.2905          # 29% of expansions; 71% go to the guided heap
```

cp#9 entered the neutral lane at expansion 5958 and waited 2042 expansions. When the budget ended, 300 live candidates still stood ahead of it, and clearing just that remainder at the observed service rate needs ~1033 more expansions that the run did not have. It is therefore **not** a late-generation problem and **not** a near-head bookkeeping problem: it is neutral-lane scheduling latency.

Corroborating context: the pending pool was saturated (`livePendingTotal = 1023` against a cap of 1024) and the neutral lane holds essentially all of it (`liveNeutralPending = 1023`), while the guided heap still carried 274 live entries.

## Withdrawal of the coverage conclusion

The owner rejected `MT4_LIMITATION_IS_NOW_COVERAGE`, and this round confirms why:

```ini
FIRST_CAUSAL_BOTTLENECK = CP9_REGISTERED_BUT_UNEXPANDED
DOWNSTREAM_42_NEVER_GENERATED = NOT_INDEPENDENT_BLOCKERS
GLOBAL_COVERAGE_LIMITATION = NOT_ESTABLISHED
```

cp#9 is the first unexpanded prefix. The oracle's next state can only appear once the previous exact state is expanded, so the 42 downstream `NEVER_GENERATED` checkpoints are plausibly the mechanical consequence of the prefix chain breaking at cp#9 rather than 42 independent generation failures. The number 42 itself stands; the inference from it does not.

The sharpest form of the finding is the owner's framing: cp#9's exact state **was covered** - the canonical node exists, is registered, and is retained. Coverage is not what failed here.

## What this establishes, and what it does not

Established:

- The survival taxonomy no longer mislabels a live registered twin as a duplicate, on unit micros and on real data in both arms.
- cp#9 registers at 5958, is retained, is never guided-admitted, and ends 2042 expansions later still 300 live candidates from the neutral head. Deterministic across runs.
- The neutral lane receives ~29% of expansion slots while holding essentially all of the saturated pending pool.

**Not** established:

- **No causal claim that a scheduler change would fix MT4.** `S_B` describes *where the retained node sat*, not that serving it would have reached MT4.
- No claim about whether the neutral share (0.2905) is too low or about what it should be. `NEUTRAL_EVERY` was not touched and no tuning is proposed here.
- MT4 is still a MISS. No capability claim of any kind.
- The 300-ahead figure is a single fixed-work snapshot at 8000 expansions, not a trajectory; the registration-time backlog was not separately recorded.
- The ~29% lane share is measured, not compared against any alternative policy.

## Correction appended by PR-5.26b Repair 1 (owner review of `95aafcc`)

The owner approved Phase 0 (the taxonomy repair) and the telemetry, but rejected
`S_B_NEUTRAL_SCHEDULING_LATENCY` as established:

```ini
95aafcc = APPROVED_WITH_NARROW_DIAGNOSTIC_CORRECTION
PR_5_26B_PHASE_0 = PASS
SURVIVAL_TAXONOMY = REPAIRED
S_B_NEUTRAL_SCHEDULING_LATENCY = PLAUSIBLE, NOT_ESTABLISHED_BY_CURRENT_CUT
LATE_GENERATION_CUT_6967 = RETRACT_AS_CLASSIFICATION_BOUNDARY
```

**The flaw.** The cut projected the **end-of-run** backlog (300) at the
**whole-run** average neutral service rate (0.2905) and subtracted from 8000. That
answers "how much longer would the residual queue take to drain from expansion
8000?" - it does **not** answer "was cp#9 registered early enough when it entered
at 5958?". The quantities needed for that second question - the queue state and
the service counters **at registration** - were never recorded. The boundary in
this document's own "Not established" list ("the registration-time backlog was
not separately recorded") is exactly what removed the mechanical basis for `S_B`.

The `CP9_REGISTERED_AT_EXPANSION = 5958 / 74% through, not late generation`
phrasing is likewise withdrawn: "74% through" has no mathematical bearing on
whether a registration is late. It is now reported as `5958_OF_8000` with
`CP9_LATE_GENERATION = NOT_YET_ISOLATED`, and
`END_SNAPSHOT_PROJECTED_DRAIN_AT_WHOLE_RUN_AVERAGE_SERVICE_RATE` is kept as a
metric but no longer defines any boundary.

**Repair 1 measured the missing quantity** and it changes the picture
substantially: cp#9 entered behind a **1027-deep** backlog (not 300), and that
backlog was **907 rank-20 / 118 rank-10 / 2 rank-30** - i.e. dominated by
combatProgress investment candidates, with essentially no ordinary neutral
exploration in front of it. See
[`docs/260913/5-26b-repair-1.md`](5-26b-repair-1.md).

Everything else here stands: the taxonomy repair, the withdrawal of the coverage
conclusion, `CP9_REGISTERED`/`CP9_RETAINED`/`CP9_UNEXPANDED`, and
`CP9_WAITED_EXPANSIONS = 2042` with `CP9_END_LIVE_AHEAD = 300`.
