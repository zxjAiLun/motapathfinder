## Design contract (frozen)

The scheduler's real FIFO contract is: "when the next neutral turn comes, expand the next still-live candidate in the neutralQueue." It needs the lane's NEXT CANDIDATE to exist, not a 16.7% storage share - the time-fairness ratio does not map onto a storage capacity ratio, and 171 (however derived) was a new heuristic mapping whose perturbation cost the MT3 gate.

```text
PRIMARY_CHANGE = FIFO_RESERVE_171 -> NEXT_FIFO_HEAD_PROTECTION

trim order:
1. goal candidates always first
2. NEXT_FIFO_HEAD = scanning neutralQueue from neutralHead, the first id that
   is still pending, not closed, not expanded - protected if capacity remains
3. all remaining slots filled exactly by the proven PR-5.25s semantics:
   guidedAdmitted > neutral, same rank by insertion
4. total kept <= cap

head selection uses NONE of: frontierGuided, guidedAdmitted, action kind,
floor, oracle keys
```

The head may be guided; if it is expanded via the guided heap first, the next trim's protection advances to the next FIFO candidate - the mechanism maintains `FIFO_LANE_HAS_A_NEXT_CANDIDATE = TRUE` dynamically, not a fixed storage share. With no frontierSet (pure FIFO control) there is no head concept and the trim degenerates to the previous behavior.

Telemetry shrinks to four fields (the 171-era `fifoReserveTarget / fifoReserveKept / droppedByRetentionLane` are retired):

```ini
fifoHeadProtectionOpportunities              # trims where a live head was identified
fifoHeadProtected                            # trims where the head ended up kept
fifoHeadWouldHaveDroppedWithoutProtection    # trims where protection changed the keep set
fifoProtectedNodeWasGuided                   # protected-because-needed heads that were guidedAdmitted
```

## Results

### Phase 1 - micros under the head contract: PASS

- Starvation scenario restated: cap=6, F (earliest FIFO candidate, only goal path) + G1..G6 (guidedAdmitted dead ends) - `NEXT_FIFO_HEAD = F`, protection keeps F, goal found, exactly one drop (G6, displaced), `fifoHeadWouldHaveDroppedWithoutProtection = 1`, `fifoProtectedNodeWasGuided = 0`.
- New turnover micro: cap=2; the first-generation FIFO candidates (H, G1 - both guidedAdmitted) are consumed via the guided heap before any contested trim; the contested trim's head is C1, a MID-RUN-created neutral that the pure fill would drop behind G2/G3; protection advances to C1 and keeps it; the goal is reachable only through C1 (`fifoHeadWouldHaveDroppedWithoutProtection = 1`). This proves the protection tracks the neutralQueue contract - whoever is next - not a fixed node or an action class.
- PR-5.25s dominated-frontier micro: unchanged result (C survives, B dropped). Cap invariants and observer inertness: PASS.

### Phase 2 - implementation: minimal head protection

The 171 reserve logic and its telemetry are removed. The trim is now: goals first; `NEXT_FIFO_HEAD` = first id from neutralHead onward that is still pending, not closed, not expanded (queue position only); if the pure fill is full the worst kept NON-GOAL candidate is displaced to make room; then the pure PR-5.25s fill (guidedAdmitted > neutral, same rank by insertion). Total <= cap.

## Findings and boundaries

- The two failed mechanisms now bracket the design space precisely: **head-only protection is too weak** (cp#8 was never the head; 0 interventions on MT4), while the **171-slot reserve was too strong** (its displacement cost broke the MT3 path). Checkpoint #8 needed to survive as a NON-HEAD neutral under capacity pressure - a protection class between the two.
- `CURRENT_HEAD_MT3_CAPABILITY = REESTABLISHED_UNDER_HEAD_SURVIVAL` on this run (single run; repeatability not requalified). The 5.25s capability survives the 5.25v mechanism with near-identical trajectory (+6 expansions), unlike the 5.25u reserve.
- The MT4 miss under 5.25v is behaviorally close to the 5.25s-era MT4 miss (deepestReached=3, time-limit): with zero protections firing, the difference from the 5.25s trim is only pending-order tie-breaks, so this run's figures are consistent with the pre-5.25u MT4 picture.
- Expansion counts across time-limited runs vary with machine speed (7,194 in the uninstrumented PHASE_4 run vs 7,896 in the instrumented audit run of the same configuration); per the PR-5.25u correction, throughput comparisons across different runs are NOT machine-speed evidence. cp#8's fate is determined by early deterministic trims (depth 9), so the audit conclusion is robust to the cut point.
- Single runs; no tuning; per the predeclared gate, `IF #8 STILL DROPPED -> STOP`.
