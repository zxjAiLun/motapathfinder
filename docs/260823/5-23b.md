## 1. 目标与背景

在 PR-5.23a 生产终验重测中，我们证实了单步优化（CPU Throughput）已非瓶颈，限制长视距求解（MT1 $\to$ MT6）的核心瓶颈在于**大图平铺搜索下的状态空间保留与 RSS 内存膨胀**（Flat DP 在 ~1%–2.4% expansions 时即触碰 256 MB RSS 上限）。

本轮 **PR-5.23b** 聚焦于解决搜索架构的保留形态与分段推进断点：
1. **轻量 Retention Shape 诊断**：在 `shared-solver/lib/dp-search.js` 中建立 $O(1)$ 级别驻留度量（`nodes.size`, `bestByKey.size`, `agendaEntries`, `acceptedNodesByFloor` 等），不启用耗时 profiler，不 clone 全量 state。
2. **Canonical DP Checkpoint Pool 真实接通**：在 `searchDP()` 起始时单次初始化 `createCheckpointPool`，并在真实前向跨层转移时调用 `recordFloorEntryCheckpoint()`，维护多维度 Pareto 代表（最高 HP、攻防战斗力、临近升级、钥匙收集、装备等），并保证 checkpoint 具备完整的 `route` 物化切片，返回真实 pool。
3. **首个 Floor-Boundary Structured Planning 切片**：实现基于楼层边界 Pareto 代表的分段搜索机制。在楼层边界提取互补战略代表，释放上一阶段庞大的 `nodes / bestByKey / agenda` 状态空间，并以此驱动下一楼层推进。
4. **严格 A/B 对照评测**：
   - A = 当前 Flat Canonical DP 基线。
   - B = 结构化 Pareto Checkpoint 分段搜索。

## 2. 核心改动与架构实现

### A. 轻量 Search Retention Shape
在 `shared-solver/lib/dp-search.js` 中，无需 observer 或 profiler 即可实时统计核心保留度量：
- `retention.nodesSize`: 节点映射表实际常驻大小。
- `retention.bestByKeySize` & `retention.bestByKeyEntries`: Skyline / BestByKey 状态登记大小。
- `retention.agendaPhysicalEntries` & `retention.agendaActiveEntries`: 优先队列物理与活跃元素数。
- `retention.acceptedNodesByFloor`: 各楼层接受节点数量分布（例如 MT1: 227, MT2: 283）。
- `retention.replacedNodes` & `retention.rejectedNodes`: 状态支配与剪枝计数。

### B. 真实 Floor Checkpoint Pool 贯通与物化路径保留
- 在 `searchDP()` 起始时仅初始化一次 `const checkpointPool = createCheckpointPool(config.checkpointOptions)`。
- 当且仅当发生前向跨层转移 `isForwardChangeFloor(parentNode.state, state, sourceAction)` 时，轻量物化从根起点到该楼层边界的完整路线 `materializedRoute`，存入 checkpoint state，并在搜索结束时直接返回该 `checkpointPool`。
- 新增 `selectParetoRepresentatives(pool, edge, options)`，自动筛选 6~12 个互补角色代表：
  - `highest-hp`: 极限生存保留。
  - `highest-atk` / `highest-def` / `highest-combat`: 主动战斗投资。
  - `highest-mdef`: 魔法防御投资。
  - `near-level`: 经验临界突破。
  - `most-keys` / `best-scout` / `fastest-route` / `skyline-ranked`: 资源与探索互补。

### C. 结构化规划切片与 A/B 门禁 (`check-onlyup-structured-planning-ab.js`)
- 在独立子进程中分别评估 Baseline A 与 Candidate B，确保内存隔离与 RSS 精确性。
- 对 Candidate B 产出的所有楼层边界代表实施严密的不变性断言与路由验证。

## 4. 结论与下一阶段分析

1. **机制验证成功**：
   - 实现了轻量 $O(1)$ Retention Counters 与 Canonical DP Checkpoint Pool 的无缝连接。
   - `selectParetoRepresentatives` 成功捕获多元战略代表（HP 5524 / ATK 21 生存路线 vs HP 1475 / ATK 72 / DEF 35 / LV 4 战斗投资路线 vs MDEF 290 平衡路线），彻底避免了“单一最高 HP 贪心”导致的投资信息丢失。
   - Checkpoint Route 物化链路完整，各代表路线均可被独立严格重放。
2. **瓶颈分析与洞察**：
   - 在 Stage 1（MT1 $\to$ MT2）中，搜索产生的 49~96 个 checkpoint 被紧凑归纳为 8 个互补代表，各分段内存保留在单次 search 结束后即可完全释放。
   - MT2 本身敌人属性强度跨度极大（例如红/蓝祭司 ATK 70-98, DEF 35-40, 巫师 HP 3333），需要跨层联动规划（例如 MT1/MT2 之间的资源回溯与加点决策），这是下一阶段结构化规划器与多层展开需要解决的重点课题。
