## 1. 目标与背景

在 PR-5.23c 中，我们证实了 Pareto 多样性代表在干净独立的子进程环境下的公平搜索行为：
- **省血/快速路线**：具有较大的搜索空间（frontier 仍存），展开至受限于时间/扩展上限；
- **高攻/高防/高魔防投资路线**：在仅展开 3~51 步后即出现 **`frontier-exhausted`**（合法动作耗尽，搜索完备终止）。

本轮 **PR-5.23d** 核心目标：
1. **失败驱动的跨层修复规划（Failure-Driven Cross-Floor Repair Planning）**：
   - 拒绝向已经 `frontier-exhausted` 的投资代表重复投入无效正向算力；
   - 直接复用现有 `adaptive-segment-planner.js` 与 `resource-intent-scanner.js`，将真实 Stage 2 失败输入（`target-action-unreachable`）转化为跨层修复规划分支（`path-blocker`, `stat-atk` 等）；
   - 允许楼层信封（Floor Envelope）自动推导为 `["MT1", "MT2"]`，允许跨层移动（`changeFloor` / `floorFly` / `battle` / `pickup` / `event` 等）。
2. **主动投资重试（Active Investment Retry）**：
   - 真实执行修复分支搜索，验证修复后状态与路径的 Strict Replay（100% 从真实 MT1 起点重放验证）；
   - 从修复后的状态再次启动向 MT3 的前向搜索探索。
3. **全局单一父进程权威预算硬控制**：
   - Stage 1、Stage 2 公平搜索、跨层修复搜索、主动重试搜索全链路共享单一 30,000 ms 墙钟（父进程端到端测量）与 50,000 expansions 上限，单进程 256 MB RSS 阈值。

## 2. 核心架构改动与实现

### A. 种子失败证据与跨层修复规划接入（`check-onlyup-structured-planning-ab.js`）
- 在 `runSingleRepresentativeSubprocess` 中保留轻量序列化种子失败证据（`bestProgressState`, `bestProgressRoute`, `bestProgressExactStateKey`, `frontierSize`, `terminationClass`）。
- 对 `terminationClass === "frontier-exhausted"` 的 6 个代表，调用 `buildRepairSegments()`，自动生成跨层修复段（`allowedFloors: ["MT1", "MT2"]`）。
- 派生独立子进程 `runRepairSubprocess` 执行修复搜索，产出修复后的状态与路线。
- 对修复后状态执行 Strict Replay（`verifyRepresentativeStrictReplay`），并再次派生子进程执行 `retry` 前向搜索。

### B. 权威预算动态下发（Authoritative Budget Manager）
- 在派生任何子进程前，父调度器实时计算剩余预算：
  ```js
  const remainingWallMs = WALL_LIMIT_MS - searchOrchestrationWallMs;
  const remainingExpansions = MAX_EXPANDED_STATES - globalExpansions;
  ```
  若 `remainingWallMs <= 500` 或 `remainingExpansions <= 0`，主动终止调度并标记 `budgetExhausted = true`。

## 4. 科学结论与事实冻结

1. **机制全面合格（Mechanism Qualified）**：
   - 跨层修复规划（Cross-Floor Repair Planning）成功打通，复用 `resource-intent-scanner` 与 `adaptive-segment-planner` 自动生成了 `path-blocker` 与 `stat-atk` 修复分支。
   - 全部 6 个修复分支的重放验证 100% 通过（`repairStrictReplay: true`）。
   - 全链路严密受控于父进程 30s / 50k 预算（实测 20.5s / 3432 expansions，峰值 RSS 仅 210MB，零透支）。
2. **能力边界结论**：
   - 修复分支搜索虽然成功生成并执行，但在当前 MT2 怪物数值门槛下，重试前向搜索仍未产生通往 MT3 的 checkpoint（最深停留 `MT2`）。
   - 说明当前单纯基于就地 `path-blocker` / `stat-atk` 单步意图修复尚不足以弥补击破 MT2 关键拦路怪（如蓝祭司 70 ATK / 红祭司 98 ATK）所需的复合数值缺口。
   - `promotion: false`，为后续多阶段复合回滚与全局窗口修复（Adaptive Window Repair / Multi-Milestone Rollback）提供了确凿的方向依据。
