## 2. 瓶颈机制剖析（Why is `battleScan` / `hazardBuild` slow?）

通过对 `shared-solver/lib/auto-actions.js` 的源码审计，发现以下完全等价的可优化冗余：

### 瓶颈 1: 单次 Pass 内危害图（Hazards）的无谓重复构造
在单次 `runAutoPickupPass` 与随后的 `runAutoBattlePass` 中：
1. `collectAutoPickupTargets` 构造一次 `hazards`。
2. 紧接着在同一状态下（若无 pickup 发生），`collectAutoBattleTargets` **再次调用 `buildMovementHazards` 重新构建完全相同的危害图**。
3. 在 `runAutoBattlePass` 遍历 `targets` 时，每次循环内部 **又调用了一次 `this.buildHazards`**。
- **等价优化**：在单次稳定化步骤中，若 state 未发生改变（无 mutation / 无拾取 / 无战斗），共享同一个 `hazards` 实例；仅在状态发生转移后按需重新构建。

### 瓶颈 2: `collectTargets` BFS 队列中的 `Array.shift()` O(N) 开销与分配
- `shared-solver/lib/auto-actions.js` 中的 `collectTargets` 使用 `queue = [...]` 和 `queue.shift()`，每次 shift 都会引发数组元素前移（O(N) 开销）和频繁 GC 压力。
- **等价优化**：改用 cursor 索引（`queue[cursor++]`）遍历固定大小队列，消除 `shift` 带来的数组重排。

### 瓶颈 3: `evaluateAutoBattleTarget` 的提前快速跳过（Pre-check Fast Path）
- 每次 BFS 访问到敌人瓦片时，立即调用 `battleResolver.evaluateBattle(state, floorId, x, y, tile.id)`。
- 自动战斗的前提是**无伤（0 战损）且无特殊阻断技能**：
  - `AUTO_BATTLE_BLOCKED_SPECIALS` 已静态定义。
  - 对于明显不可能 0 伤害的怪物（例如当前英雄攻击力 <= 怪物防御力 `state.hero.atk <= enemy.def`），可静态直接跳过 `evaluateBattle` 完整模拟。
  - 敌人存在性与瓦片类型静态预检。

## 3. 优化设计方案（Optimization Design）

### 设计 A: 同 Pass 共享 Hazard 上下文（Scoped Hazard Reuse）
在 `runAutoPickupPass` 与 `runAutoBattlePass` 之间传递/复用当前状态下的 `hazards`：
- 若 `runAutoPickupPass` 未触发任何拾取（`changed === false`），直接将已构建的 `hazards` 传递给 `runAutoBattlePass`，避免重复计算。
- 消除 `runAutoBattlePass` 循环体内部每次对 `this.buildHazards` 的冗余调用。

### 设计 B: `collectTargets` 队列索引化（Zero-Shift BFS Queue）
- 使用 `head` 指针代替 `queue.shift()`。
- 使用坐标整数哈希或扁平标记代替字符串 Set 键（保持跨平台/Node 纯 JS 语义）。

### 设计 C: 0-Damage 自动战斗静态前置剪除（Static 0-Damage Pre-filter）
在调用 `battleResolver.evaluateBattle` 之前执行等价快速拒绝：
1. `hasAnySpecial(enemy, AUTO_BATTLE_BLOCKED_SPECIALS)` -> 立即拒绝。
2. 基础攻防硬检查：若怪物有防且 `hero.atk <= enemy.def`（必然破不了防或无法 0 伤），直接返回 `null`，无需进入复杂战斗结算器。
