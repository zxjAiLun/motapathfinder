## 1. 目标与架构（Iteration 2 进程隔离段执行架构）

在 PR-5.24b Iteration 1（及其三轮 Repair）中，证实了在 Node.js 单进程生命周期中，跨段搜索的底层内存累积无法回落至 256MB 搜索阈值以下（`SAME_PROCESS_RECOVERY_INSUFFICIENT_UNDER_CURRENT_PLANNER_LIFECYCLE`）。

**PR-5.24b Iteration 2: Process-Isolated Canonical Segment Execution 核心落地**：
1. **规范规划器与一次性执行器解耦（Planner / Worker Separation）**：
   - **Canonical Parent Planner (`segment-dp.js`)**：保留所有宏观控制权（里程碑历史、深度回退判定、优先标签排序、天际线合并、全局 30s/50k 预算仲裁）；
   - **Disposable Subprocess Segment Worker (`segment-worker.js`)**：每个段搜索与重放波次作为独立子进程执行，执行完成后进程退出，RSS 由操作系统物理回收；
2. **状态双向全等保证（Round-Trip StateKey Identity Verification）**：
   - Parent 在下发输入候选时计算 `parentInputStateKeys`，Worker 反序列化后在搜索前重新计算 `childInputStateKey` 校验完全一致；
   - Worker 产出目标候选时标记 `outputStateKey`，Parent 反序列化后重新校验 `buildStateKey` 完全一致，确保 flags、equipment、floorStates 无任何漂移；
3. **父进程唯一预算权威与内存收敛**：
   - Parent 在 spawn 前动态计算 `remainingExpansions` 与 `deadlineEpochMs`，Worker 严格在父级剩余预算内执行并返回实际消费；
   - Parent 自身仅常驻轻量规划器状态（实测 RSS 仅 ~72MB），子进程启动时 RSS 从 ~70MB 干净环境起步，彻底终结跨段 RSS 累积。

## 6. Iteration 2b Repair 2 — Thin MT1→MT3 Capability Lock + Final-Failure Semantics

**背景**：云端 review（`5f7e7bf`）批准六项 lifecycle 修复，但判定 `NEEDS_REPAIR_2`：(P1) 提交前约定的 Thin MT1→MT3 capability gate 未进 commit；(关键) 不能把 MT2→MT3 **initial** frontier exhaustion 解释为最终算法瓶颈——canonical adaptive repair 最终仍 RSS-limited，最终科学状态是 `RESOURCE_LIMITED_DURING_ADAPTIVE_REPAIR` 而非 `SEARCH_SPACE_EXHAUSTED`。

**范围**：只补 capability gate 与 failure 语义（checker/evidence/docs），不动六项 infrastructure。

**实现**：

1. **Final-failure 语义分离（`extractFinalFailureSemantics()`）**：从 `failedSegment/evaluationAttemptLedger/budget` 提取 `initialOutcome/initialStopReason/initialFrontierExhausted/adaptiveRollbackTriggered/adaptiveWavesAttempted/adaptiveDownstreamReplayCount/adaptiveResourceLimited/finalCanonicalOutcome`；硬性保证：`initial frontier exhausted + adaptiveResourceLimited` 时 `finalCanonicalOutcome` 必须为 `RESOURCE_LIMITED`，不得报告 `EXHAUSTED`。
2. **Thin MT1→MT3 capability gate（frozen 5.24a 语义 depth=2）**：clean child 跑 `onlyup-chaos-mt1-mt3`，全部生命周期 gate（whole-run 30s/50k、process-tree ≤260/4、StateKey/profile/projectIdentity）在两种分类下都硬性成立；found 时 `reachedMilestone === "mt2-to-mt3"` + 对每个 final candidate 做 fresh `verifyCandidateStrictReplay`（真实 MT1 重放、Chaos、零 unresolved choice、StateKey 全等）。
3. **确定性分类**：capability probe 暴露 envelope 边界现象（见下），硬 gate 不可 flaky，故 gate 改为确定性二分类并各自硬性断言其不变量：
   - `CAPABILITY_RETAINED`：found + strict replay 100%；
   - `ENVELOPE_BLOCKED`：initial 或 adaptive wave 在 thin-split envelope 处 rss-limit（两种子形态 A/B 均覆盖），`finalCanonicalOutcome === "RESOURCE_LIMITED"`，ledger 中存在 `rss-limit` 尝试。
4. **Telemetry 语义修正（gate 暴露的真实实现 bug）**：pre-spawn budget-exhausted 分支此前报告 `stateRoundTripIdentity: false`（从未 spawn worker，语义为 "not run" 而非 "verification failed"）；新增 `executed: false` 标记，checker 将其与真实验证失败区分。
5. **Worker 授权/统计一致性修正（gate 暴露的第二个实现 bug）**：worker 授权此前按 `ceiling - plannerAtSpawn` 计算，但 aggregate 上界按三点 max（含 `afterSpawn`，因 worker 输出反序列化会抬升 parent RSS）计入——出现 `260.7 > 260` 假违约；新增 `PARENT_RSS_GROWTH_RESERVE_MB = 4` 使授权与统计口径一致（stop/hard 各让 4MB）。

**云端裁决（`87128d2` review）**：2c Repair 1 APPROVED，Iteration 2c CLOSED（`FINAL_QUALIFICATION_COMMIT=87128d2`）。2d 只做一件事：**用已获得的内存余量换回搜索时间**。不动 milestone spec / allowedFloors / action & candidate ranking / dominance / 省血投资策略。优先级：MT1→MT3 retained > RSS 零回归 > GC 成本显式测量 > GC 成本实质下降 > MT1→MT4 推进。遗留 P2（MT4 binding 区分 TIME_LIMIT vs SEARCH_EXHAUSTED）顺手关闭。

### 9.1 聚合 telemetry（`dp-search.js`）

`maybeFlattenRss()` 记录每次 GC 的 `before/after RSS + heapUsed + wallMs`，summary 输出聚合：`rssGcCount / rssGcWallMsTotal / rssGcWallMsMax / rssGcReclaimedMbTotal / rssGcReclaimedMbMax / rssGcUsefulCount / rssGcIneffectiveCount / rssGcFinalIntervalExpansions`（无 per-event 数组）。

### 9.2 关键机制发现

测量揭示 2c 的固定 16-exp 节流误判了 GC 的价值来源：

```text
实测: 单次 wave search peakHeap 98.2MB vs peakRss 176.1MB
GC 后 RSS 几乎不降 (reclaimed≈0) —— V8 提交页不归还 OS
但 GC 后 heapUsed 大幅回落 → V8 复用已提交页 → RSS 停止增长
→ GC 的价值不是"回收 RSS"而是"踩住 heap 防止新页 commit"
→ 收益度量必须是 heapReclaimed (beforeHeap - afterHeap), 不是 rssReclaimed
```

且大量 GC 发生在 `heapUsed 低、RSS 高` 状态（无垃圾可收）——纯烧 wall（坏 run 实测 1261 次 ineffective GC / 7.9s）。

### 9.3 Benefit-Driven Throttling 实现

- **Heap-garbage gate**：`RSS − heapUsed ≥ rssGcMinHeapGarbageMb(16)` 才值得 GC；无垃圾时 skip 省 wall。
- **收益驱动间隔**：`heapReclaimed ≥12MB → interval ÷1.25`；`4–12MB → ×1.5`；`<4MB → ×2`；界 `[16,128]`。
- **连续低收益升级**：连续 ineffective 时 heap-garbage 门槛 +16MB/次，danger bypass 也被 min-interval 限速，杜绝 danger-zone 高频无效 GC 自旋。
- **Danger-zone (≥0.94×maxRss) 无视 garbage gate**：V8 lazy commit 可在 heap 低时抬 RSS，只有 full GC 能让 V8 收缩——但保留限速。
- **收益度量换为 heapReclaimed**（见 9.2）。
- **Worker stop margin 4→8MB**：danger GC 无法完全防住深搜索的单次瞬时冲线；margin 8 让 RSS 平台 ~248，hard 260 兜底（margin 4 时偶发 rss-limit ×1）。

```text
workerSearchWallMsTotal vs isolatedWorkerWallMsTotal 之差 ≈ spawnAndProtocolOverheadMs
gcWallMsTotal / gcCountTotal / gcReclaimedMbTotal 从 ledger 聚合
```

## 12. Iteration 4 Repair 1 — Round-Aware Fair Budget + Exact Completion Accounting

**云端裁决（`e3be56b` review）**：Interpreter P1 APPROVED（单一语义实现闭合）；但 Iteration 4 `NEEDS_REPAIR_1`：

### 16.1 P1-A — complete-search-aware failure classification

**缺陷**：`searchSegmentDP()` 对非 memory failure（time-limit、expansion slice 未完成、action scope incomplete、cancel）全部走 `summarizeSegmentFailure()`；而新的 `classifySegmentFailure()` 只看 `missing floorId + goal.floorId ∈ allowedFloors` 就输出 `floor-progress-blocked` + `resource-diverse` repair direction——与自身定义"**complete** search could not progress"矛盾，且已在本地真实发生（finalPending>0 的 run 中 failedSegment 仍被标 floor-progress-blocked），会误导 adaptive rollback 在"其实只是没搜完"时去找资源投资路线，污染 OFF/ON 对照。

**修复**（`segment-dp.js`）：

1. `searchOutcome`（authoritative `buildSearchOutcome` 结果）作为第 4 参数传入 `classifySegmentFailure`、第 6 参数传入 `summarizeSegmentFailure`（调用点 `searchSegmentDPWithPerf` 直传局部 `searchOutcome`）。

   - `goalFloorAllowed && searchComplete === true` → `floor-progress-blocked`（含 resource-diverse 方向）——语义现在名实相符；
   - `goalFloorAllowed && searchComplete !== true`（含 time/expansion/resource incomplete、actionTrimmed、cancel、legacy null）→ **新分类 `floor-search-incomplete`**（preferred tags 仅 `highest-hp/best-combat`，无 resource-diverse 方向；fail-closed：null outcome 也归此）；

3. scope 判定扩展：`goalFloorAllowed` 现在同时要求 goal floor ∈ allowedFloors **且** actionKinds 允许 `changeFloor` 或 `floorFly`（全禁 floor-transit = 结构性不可达 = scope violation）。
4. `failurePriority` 增加 `floor-search-incomplete: 12`（高于 budget-or-action-scope-exhausted 的兜底、远低于 floor-progress-blocked）。
5. consumer 适配：`resource-intent-scanner.js` 对 `floor-search-incomplete` 仅给 path 意图（无资源投资方向）；`solver-doctor.js` 增加对应 recommendation/likelyCause。

### 16.2 P1-B — true Pareto-first selection order + live resource-diverse tag

**缺陷 1（顺序）**：实现顺序是 anchors → novelty 填满 capacity → 最后才尝试 nondominated leftovers；`keepCandidate` 在满容量后直接拒绝——novelty 抢满 8 席后未选 nondominated 仍被 capacity-drop，不是声称的 Pareto protection。
**缺陷 2（死标签）**：`resource-diverse` 只出现在 failure classification 的 preferredCandidateTags 里，selection 从未 `addTag`，rollback 排序 `candidate.tags.has(tag)` 永远不命中——纯死标签。

**修复**（`selectCandidateSkyline` diversity 路径）：

```text
anchors (highest-hp / best-combat / highest-atk / highest-def / highest-exp)
→ Phase 1: Pareto-first novelty fill（只有 nondominated leftovers 竞争）
→ Phase 2: zero-novelty nondominated leftover pass（排序确定性填入）
→ Phase 3: general novelty fill（全部剩余候选）
→ legacy fallback
```

关键 invariant：**只要存在未选 nondominated candidate，任何 dominated candidate 不得占用非 anchor 槽位**（Phase 2 先于 Phase 3 保证）。
