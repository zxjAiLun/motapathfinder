## 1. 目标与架构（Iteration 2 进程隔离段执行架构）

在 PR-5.24b Iteration 1（及其三轮 Repair）中，证实了在 Node.js 单进程生命周期中，跨段搜索的底层内存累积无法回落至 256MB 搜索阈值以下（`SAME_PROCESS_RECOVERY_INSUFFICIENT_UNDER_CURRENT_PLANNER_LIFECYCLE`）。

**PR-5.24b Iteration 2: Process-Isolated Canonical Segment Execution 核心落地**：
1. **规范规划器与一次性执行器解耦（Planner / Worker Separation）**：
   - **Canonical Parent Planner (`segment-dp.js`)**：保留所有宏观控制权（里程碑历史、深度回退判定、优先标签排序、天际线合并、全局 30s/50k 预算仲裁）；
   - **Disposable Subprocess Segment Worker (`segment-worker.js`)**：每个段搜索与重放波次作为独立子进程执行，执行完成后进程退出，RSS 由操作系统物理回收；
2. **状态双向全等保证（Round-Trip StateKey Identity Verification）**：
   - Parent 在下发输入候选时计算 `parentInputStateKeys`，Worker 反序列化后在搜索前重新计算 `childInputStateKey` 校验完全一致；
   - Worker 产出目标候选时标记 `outputStateKey`，Parent 反序列化后重新校验 `buildStateKey` 完全一致，确保 flags、equipment、floorStates 无任何漂移；
3. **父进程唯一预算权威与内存收敛**：
   - Parent 在 spawn 前动态计算 `remainingExpansions` 与 `deadlineEpochMs`，Worker 严格在父级剩余预算内执行并返回实际消费；
   - Parent 自身仅常驻轻量规划器状态（实测 RSS 仅 ~72MB），子进程启动时 RSS 从 ~70MB 干净环境起步，彻底终结跨段 RSS 累积。

## 6. Iteration 2b Repair 2 — Thin MT1→MT3 Capability Lock + Final-Failure Semantics

**背景**：云端 review（`5f7e7bf`）批准六项 lifecycle 修复，但判定 `NEEDS_REPAIR_2`：(P1) 提交前约定的 Thin MT1→MT3 capability gate 未进 commit；(关键) 不能把 MT2→MT3 **initial** frontier exhaustion 解释为最终算法瓶颈——canonical adaptive repair 最终仍 RSS-limited，最终科学状态是 `RESOURCE_LIMITED_DURING_ADAPTIVE_REPAIR` 而非 `SEARCH_SPACE_EXHAUSTED`。

**范围**：只补 capability gate 与 failure 语义（checker/evidence/docs），不动六项 infrastructure。

**实现**：

1. **Final-failure 语义分离（`extractFinalFailureSemantics()`）**：从 `failedSegment/evaluationAttemptLedger/budget` 提取 `initialOutcome/initialStopReason/initialFrontierExhausted/adaptiveRollbackTriggered/adaptiveWavesAttempted/adaptiveDownstreamReplayCount/adaptiveResourceLimited/finalCanonicalOutcome`；硬性保证：`initial frontier exhausted + adaptiveResourceLimited` 时 `finalCanonicalOutcome` 必须为 `RESOURCE_LIMITED`，不得报告 `EXHAUSTED`。
2. **Thin MT1→MT3 capability gate（frozen 5.24a 语义 depth=2）**：clean child 跑 `onlyup-chaos-mt1-mt3`，全部生命周期 gate（whole-run 30s/50k、process-tree ≤260/4、StateKey/profile/projectIdentity）在两种分类下都硬性成立；found 时 `reachedMilestone === "mt2-to-mt3"` + 对每个 final candidate 做 fresh `verifyCandidateStrictReplay`（真实 MT1 重放、Chaos、零 unresolved choice、StateKey 全等）。
3. **确定性分类**：capability probe 暴露 envelope 边界现象（见下），硬 gate 不可 flaky，故 gate 改为确定性二分类并各自硬性断言其不变量：
   - `CAPABILITY_RETAINED`：found + strict replay 100%；
   - `ENVELOPE_BLOCKED`：initial 或 adaptive wave 在 thin-split envelope 处 rss-limit（两种子形态 A/B 均覆盖），`finalCanonicalOutcome === "RESOURCE_LIMITED"`，ledger 中存在 `rss-limit` 尝试。
4. **Telemetry 语义修正（gate 暴露的真实实现 bug）**：pre-spawn budget-exhausted 分支此前报告 `stateRoundTripIdentity: false`（从未 spawn worker，语义为 "not run" 而非 "verification failed"）；新增 `executed: false` 标记，checker 将其与真实验证失败区分。
5. **Worker 授权/统计一致性修正（gate 暴露的第二个实现 bug）**：worker 授权此前按 `ceiling - plannerAtSpawn` 计算，但 aggregate 上界按三点 max（含 `afterSpawn`，因 worker 输出反序列化会抬升 parent RSS）计入——出现 `260.7 > 260` 假违约；新增 `PARENT_RSS_GROWTH_RESERVE_MB = 4` 使授权与统计口径一致（stop/hard 各让 4MB）。
