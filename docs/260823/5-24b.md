## 1. 目标与架构（Iteration 2 进程隔离段执行架构）

在 PR-5.24b Iteration 1（及其三轮 Repair）中，证实了在 Node.js 单进程生命周期中，跨段搜索的底层内存累积无法回落至 256MB 搜索阈值以下（`SAME_PROCESS_RECOVERY_INSUFFICIENT_UNDER_CURRENT_PLANNER_LIFECYCLE`）。

**PR-5.24b Iteration 2: Process-Isolated Canonical Segment Execution 核心落地**：
1. **规范规划器与一次性执行器解耦（Planner / Worker Separation）**：
   - **Canonical Parent Planner (`segment-dp.js`)**：保留所有宏观控制权（里程碑历史、深度回退判定、优先标签排序、天际线合并、全局 30s/50k 预算仲裁）；
   - **Disposable Subprocess Segment Worker (`segment-worker.js`)**：每个段搜索与重放波次作为独立子进程执行，执行完成后进程退出，RSS 由操作系统物理回收；
2. **状态双向全等保证（Round-Trip StateKey Identity Verification）**：
   - Parent 在下发输入候选时计算 `parentInputStateKeys`，Worker 反序列化后在搜索前重新计算 `childInputStateKey` 校验完全一致；
   - Worker 产出目标候选时标记 `outputStateKey`，Parent 反序列化后重新校验 `buildStateKey` 完全一致，确保 flags、equipment、floorStates 无任何漂移；
3. **父进程唯一预算权威与内存收敛**：
   - Parent 在 spawn 前动态计算 `remainingExpansions` 与 `deadlineEpochMs`，Worker 严格在父级剩余预算内执行并返回实际消费；
   - Parent 自身仅常驻轻量规划器状态（实测 RSS 仅 ~72MB），子进程启动时 RSS 从 ~70MB 干净环境起步，彻底终结跨段 RSS 累积。

## 4. Iteration 2b — Thin Canonical Planner（CAPABILITY_COMMIT `d45c000`）

**架构**：thin planner 进程永不 `loadProject` / `new StaticSimulator`。一次性 `planner-bootstrap-worker.js` 导出 `{initialState, StateKey, simulatorProfile, projectIdentity}`；`isolated-segment-executor.js` 支持 `isolatedRuntimeDescriptor`（`simulator==null` 时仅凭 descriptor spawn worker）；canonical rollback/history/budget 保留在 thin 父进程（`lib/thin-planner.js`）。

云端独立 review（`d45c000`）结论：架构方向 `DIRECTION_APPROVED`，但 3 个 P1 生命周期资格缺口未闭合，判定 `NEEDS_REPAIR_1`：

- **P1-1 全局 30s 未包含 bootstrap**：`runBootstrap(timeout:30000)` 与 `runMilestoneGraph` 内部新建的 30s budget 串联，最坏 ~60s；
- **P1-2 bootstrap process-tree 公式错误**：`max(plannerRSS, workerRSS)` 低估并发（正确为 `plannerAtSpawn + workerPeak ≈ 118.7MB`），且 checker 仍只 hard gate segment-only 字段；
- **P1-3 52.9MB 非权威 RSS**：checker 顶层 require 了 `project-loader/simulator/battle-resolver`，基准被 heavy parity 污染；`thinPlannerNeverLoadsProject` 为 self-attestation。

## 5. Iteration 2b Repair 1 — Lifecycle Budget + Clean Thin Qualification

**范围**：不优化 planner 代码体积，只修 qualification（P1-1/P1-2/P1-3 + P2-1/P2-2/P2-3）。

**实现**：

1. **Whole-run deadline（P1-1）**：`runThinMilestoneGraph()` 在 bootstrap 前以 `segment-dp.js::createGlobalBudget`（新导出，未复制 schema）创建唯一 `overallBudget`；bootstrap spawn timeout 取 `deadlineMs - now` 剩余；bootstrap 超时 fail-closed 抛错；`requestedRuntimeMs` 仍报告原始 `30000`；`overallWallMs` hard assert `≤30000` 且 `≥ bootstrapWallMs`。
2. **Bootstrap 并发内存（P1-2）**：`bootstrapAggregateUpperBoundMb = max(parentAtSpawn, parentAfter) + bootstrapWorkerPeak`（并发和，非 max）；`overallProcessTreePeak = max(bootstrapAggregate, segmentAggregate)`；`processTreeMemory.qualified/overshootMb` 改基于 overall peak，checker 直接 hard assert `maxConcurrentProcessTreeRssMb ≤ 260 && overshootMb ≤ 4`。
3. **Clean RSS 测量拆进程（P1-3）**：新增 `check-thin-planner-runtime-child.js`（只 import `thin-planner`，stdin 传 config）；`check-thin-planner.js` 主进程的 heavy parity 完全分离。`neverLoadsProject/neverConstructsSimulator` 改为由 `require.cache` 计算的证据（`heavyModuleLoadedEvidence()`），checker 断言 `heavyModulesLoadedInPlannerProcess === []`。
4. **删除手写 normalization（P2-1）**：`loadMilestoneSpecThin()` 直接 `getMilestoneSpec(null, routeName)`；新增 gate：thin milestones 与 heavy `getMilestoneSpec(project).milestones` deep-equal（MT1→MT4 全量），并新增 successor `presentTiles` 传播语义 micro fixture（`propagateSuccessorHardPresentTiles` 已从 `milestone-spec.js` 导出）。
5. **projectIdentity 执行校验（P2-2）**：descriptor 携带 expected identity → segment worker `loadProject` 后重算 applied identity → parent hard assert `projectIdentityMatch`（与 `simulatorProfileIdentity` 同级；缺失 applied identity 抛错）。
6. **Envelope fail-closed（P2-3）**：`segment-worker.js` 对 isolated invocation 强制 envelope（缺文件/invocationId 不匹配/`workerMaxRssMb` 或 `workerHardCeilingMb` NaN/≤0 均 exit 5）；checker 增加 4 个负向 probe（缺 envelope、id mismatch、0 max、NaN ceiling）。
