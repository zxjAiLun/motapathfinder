## 1. 架构发现与开销精细分解

在 PR-5.22e 消除 41.97% 的 scan 权威战斗评估调用后，`stabilizeState` 的下一主要耗时热点为 `pickupApply`（约占总稳定化耗时的 20%~25%）。

### A. PickupApply 内部开销精细分解（实测数据）
在 400-expansion 真实 OnlyUp direct search 下对 `resolvePickupAt` 进行 5 个子阶段独立计时与调用计数（`shared-solver/lib/perf.js` & `shared-solver/lib/simulator.js`）：
- `pickupTileLookupMs`: $\sim 0.5\text{ ms}$（调用 728 次）
- `pickupTileRemoveMs`: $\sim 0.8\text{ ms}$（调用 728 次）
- `pickupItemEffectMs`: $\sim 340\text{ ms}$（**占 `pickupApply` 耗时的 96%+**，调用 727 次）
- `pickupAfterGetItemMs`: $\sim 0.0\text{ ms}$（调用 0 次）
- `pickupLevelUpMs`: $\sim 6.5\text{ ms}$（调用 728 次）

**核心机制结论**：
`pickupApply` 的开销 96%+ 确实由 `executeItemEffect` 中的 Node.js VM 调用引起。然而进一步分析证实，开销主要源于 Node.js V8 每次调用 `runInNewContext` 时创建全新 Context（Realm 分配与内置对象初始化）的机械开销，而非单纯代码编译。

## 2. 严格隔离的预编译 `vm.Script` 架构 (Repair 1)

为避免 `new Function` 引入的环境越界（如访问 `process`）、缺少执行超时和顶层 return 语法漂移等问题，PR-5.22f Repair 1 严格采用 `vm.Script` 缓存架构：
- **`vm.Script` 编译缓存**：以 `item.itemEffect` 源码为键在 `COMPILED_SCRIPT_CACHE`（有界 1024 上限）中缓存 `new vm.Script(code)`。
- **环境严格隔离与上下文 Freshness**：
  - 每次执行传入全新 context 对象：`{ core: buildEffectCore(project, state), Math }`。
  - 严格保持 `typeof process === "undefined"` 和 `globalThis.process === "undefined"`。
  - 连续跨状态执行时验证 `globalThis` 无任何持久污染。
- **超时保护机制**：保留 `timeout` 参数（默认 1000ms，测试可传 `timeoutMs: 20`），死循环 `while(true){}` 严格超时退出，绝不挂起主线程。
- **语法一致性**：Script 顶层 `return` 严格抛出 `SyntaxError`。
