## 问题与已有证据

接手审计与云端诊断已确立单根病理（[takeover](cloud-progress-takeover.md)、[cloud-node-route-audit](../260921/cloud-node-route-audit.md)）：neko 生产搜索为**单根** durable 搜索，Fair4（`hybrid-fair` + `fairnessEvery=4` + `fifo`）虽已明确压过 best-first，但每推进一个 teacher-prefix step 仍要把约十万个兄弟节点重新排队展开——缺少 **temporal locality**。133 attempts / 8,320,697 expansions 后最深 popped prefix 仍停在 Step 11，P12 插入 @49,945 却从未 popped；Fair4@128k 相比 64k 未推进（deepest popped prefix 均为 11）。

代码调研（committed HEAD `5a383a6` `dp-search.js`）确认：

- **Fair4 是 hybrid-fair agenda**：子节点 enqueue 时同时进 `heap`（best-first 比较器）与 `fairEntries`（FIFO）。`popNext` 每 `(expansions+1)%fairnessEvery===0` 弹出 `fairEntries` 最老未展开节点，否则弹 `heap` 最优。
- **单根**：`runAttempt` 调 `searchDP(sim, state, …)` 传单个 state ⇒ `multiRootSearch===false` ⇒ PR-5.24h 的 root-sliced quantum scheduler（`multiRootExpansionQuantum` / `popRootSliced`）在 neko 路径**是死码**，不是本轮的 prior art，也不与之竞争。
- **5.31g 已预留** `searchSemantics.continuationSlice{enabled,mode,budget}` 并纳入 `resumeSearchFingerprint`（enabled=false ⇒ mode/budget=null）。

病理机制：fair-pop 给某个饥饿的深层 winning ancestry 一次服务机会后，**紧接着的展开立即回到全局竞争**，把该方向的十万级兄弟重新排一遍，promising lineage 无法连续前进。

## 唯一因果问题

> 给一个刚通过 fair pop 获得服务的方向**一点连续的局部工作量**，是否真的能消除“每走一步重新排十万节点”的病理？

这是一个 **temporal-locality** 假设检验，不是再造 heuristic。

## 初始设计（v1 语义 — LOCKED）

### 机制（fair-pop-only,锁定原因见下）

```
fair pop 一个 root（***仅*** fair-oldest pop 触发；best-first/fifo pop 不触发）
        ↓
以 N 为界创建一个 local continuation slice
        ↓
整个局部子树共享一个总预算 K
（root 自身的 expansion 消耗单位 #1；K 次为界的局部 expansion 中，下一个
  展开对象从「本 slice 内新产生且存活」的局部前沿里按现有同一比较器选取）
        ↓
K 次 expansion 用完（或局部前沿枯竭）
        ↓
仍存活的状态正常回 global agenda（heap + fairEntries，一如既往）
```

补充（fair-pop-only 裁定）：best-first pop 本就沿最优 rank 连续深入，没有「被服务一次后立刻丢回全局竞争」的病；"被服务一次后立刻掉回全局" 只发生在 fair-oldest pop 把某个看似饥饿的深层 winning ancestry 弄出来一次之后。切片只钩在 fair pop 上，是最对症、改动最小的 causal test；两臂的 best-first pop 路径逐位一致。

### 硬约束（防止重演 5.31d/e）

1. **subtree 共享总预算 K**，不是“每个 child 各自获得 K”。否则 branching factor 会把额度乘起来。
2. **不继承永久优先级**：slice 结束后存活状态回到全局 agenda 的正常位置，没有任何跨 slice 的持久优先权。
3. **K 从同一全局 `maxExpansions` 预算扣**，不是额外预算。这样 Control 与 Treatment 在**相同总工作量**下比较，A/B 才是单变量。
4. **slice 内沿用现有搜索语义**：同一 DP key、同一 dominance、同一 goal-relative 比较器、同一 action generation、同一 archive/skyline。第一版**禁止**新增：resource score、TS12 特判、回楼奖励、ATK/宝石阈值。测的是 temporal locality，不是另造启发式。
5. **默认 OFF**：`continuationSlice.enabled` 未开时，搜索路径必须与当前逐位一致（behavior-preserving）；child 处理（注册/skyline/dominance/goal archive/heap/fairEntries）在开/关两态下都完全相同，slice 只改变“下一个展开谁”。

### K 首值

不做参数扫表。由代码结构选一个**小而自然**的首值，让一次 slice 机会有**几十次**局部 expansion（不是几千）。第一轮只允许 one K / one treatment / one 32k run。观察的是机制是否成立，不是找“最佳 K”。

## 第一轮 causal control（LOCKED）

Control 不回 best-first（已被 Fair4 压过）。第一轮单变量对照：

```
Control    : Fair4  (hybrid-fair + fairnessEvery=4 + fifo)
Treatment  : Fair4  +  bounded continuation slice (one K)
```

其它全部一致：same exact durable seed / DP key / dominance / goal-relative comparator / action generation / archive / expansion budget（32k）。

### 预算：32k（不是 128k）

Fair4@32k 已知基线：`P7=143, P8=1467, P9=10651, P10=queued`。

## 预冻结判据（三态）

**成功信号（→ 授权 64k 复算）**：
- P7 / P8 / P9 不明显退化；
- P10 在 32k 内被 **popped/展开**；
- P11 / P12 不再重新产生数万级等待；
- deepest exact prefix 明显 **> Step 9**。
- 最好直接 `foundGoal=true` → materialize actual route → strict replay PASS。

**负信号（→ 记负结果，停止，不扫 K）**：
- 只是多展开了大量局部兄弟；
- frontier / wall-time 暴涨；
- teacher prefix 没明显推进。

**中间（inconclusive）**：deepest prefix 有小幅推进但未达 P10 展开 → 记录，交 owner 判是否值得一次 64k，不自动扫 K。

## 隔离与部署边界

- 第一轮是**独立 probe**（用 5.31g 建立的执行隔离契约），**不是 production deployment**。
- probe 用 **fresh run-dir / fresh provenance / fresh searchSemantics fingerprint**；**绝不 resume** 已 `SEARCH_SEMANTICS_DRIFT` 的旧 neko 账本；旧 paused neko run 只读保留。
- 只有 probe **明确正收益**（相同工作量下恢复更多连续 winning ancestry，最好 foundGoal + strict replay PASS）后，才把 5.31g + 5.31h + 5.31i + 5.32a 一起制作**全新 production release**。
- probe 负向：5.32a 不需为此发生产 release；5.31g/h/i 已在 GitHub，等下一次真实搜索能力变化时一并部署。
