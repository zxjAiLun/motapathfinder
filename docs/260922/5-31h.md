## 问题与已有证据

接手审计（[cloud-progress-takeover](cloud-progress-takeover.md)）用正确 Neko 项目做 TS14 59 步 live replay，在第 1 步之前就失败：

```text
Initial live snapshot mismatch: initial.flags.shop1: type mismatch (undefined !== number)
Expected initial flags: { autoBattle,jc19f5,nowatk,nowlevel,saltygreen,shiqu,__leaveLoc__ }
Actual   initial flags: { ...expected..., shop1: 1 }
```

`shop1=1` 来自 `project/floors/Start.js` 首访引导（`flag:shop1`）。`restoreRuntimeSnapshotStart` 只 `core.setFlag(key,value)` 逐个**加入** snapshot 的 flag，从不清理 runtime Start 引导态里 snapshot 没有的 flag。结果是：

```text
runtime Start boot flags  ∪  snapshot flags   （merge）
```

而契约应是：

```text
snapshot-authoritative replacement
→ restored 的可表示 flag 投影 == snapshot.flags
```

`shop1` 只是第一个暴露该契约错误的症状，不是要特判删除的对象。

## 初始设计

- 只改恢复路径的 flag 处理：**先清理**运行时里“可表示且不在 snapshot”的 flag，**再**逐字应用 snapshot flag。可表示判定与 `captureRuntimeSnapshot` 的投影规则一致（丢弃 `__`-前缀内部 flag，但保留 `__leaveLoc__` 与 `_buff__`；丢弃 null/0/object）。
- 引擎内部非可表示 flag（如 `__` 内部态）**保留**，snapshot 从不建模它们。
- `autoBattle` 仍由其后独立的自动化步骤设置，恢复路径不动它（与现状一致）。
- 抽出纯函数 `restoreStartFlags(currentFlags, snapshotFlags)` 承载“清理+应用”的权威语义，供 checker 单元验证；浏览器 `page.evaluate` 内以相同规则就地清理/应用（无法跨 Node/browser 复用同一函数体，规则以注释绑定，集成门用真实 live replay 兜底）。

- 现有 strict replay / state-key 比较逻辑复用，不新造审计框架。
- 若修复后 59 步 witness 结果变化，不为绿测迁就；说明旧 witness 起点确受污染，需重新确认其 canonical replay。

### 新发现（独立变量，本轮未授权修）
- 前因：本路线 record 的 `start.snapshot.hero` 含 `equipment:[]` 但**无 `followers` 键**；`captureRuntimeSnapshot` 总是输出 `followers:[]`。`diffRouteSnapshot→diffSnapshots` 做严格 `typeof` 对比，`undefined !== object` 即报错。
- 为何之前被掩盖：顶层 diff 按键名排序，`flags` < `hero`，旧的 shop1 mismatch 先报 → 掩盖了 hero.followers。**这是 pre-existing，非本轮 flag 修复引入**（flag 修复不碰 hero 比较）。
- 分类：属 snapshot-schema/normalization 对称性，即本轮非目标中的“其它 replay schema 历史问题”，**不属 flag 权威恢复家族**，不归入 5.31h。
- 精确修复形状（待授权）：在 `normalizeRuntimeSnapshotPair` 将 hero 数组型字段（equipment/followers）缺失视为 `[]`（与已有空 floor-record 对称处理同型）；或重建时为该 record 补写 followers。建议单独小轮（如 PR-5.31h-2 / 5.31i），不在本轮顶风口。
- 路线/见证本身仍健康：`reverify-witness.js` 的 59 步内部 strict replay 在冻结与当前代码上均 PASS（不走 live-replay 恢复路径），不受本变量影响。
