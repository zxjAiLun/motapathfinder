## Iteration 1 — hazardBlockIndex Reference-Identity Memoization

### 优化目标

`buildBlockIndex()` 在 `stabilization` 内消耗 1,966ms (fast path)。每次调用遍历整个楼层 (13×15 = ~195 cells)，总调用 16,799 次 = ~3.2M cell iterations。

### 优化实现

**文件**: `shared-solver/lib/movement-hazards.js`

**机制**: 以 `floorState` 对象引用身份作为缓存键，将 `buildBlockIndex` 结果以不可枚举属性 (`__blockIndexCache`) 存储在 `floorState` 对象上。当且仅当 `floorState` 对象引用相同时直接返回缓存结果。

**等价性保证**:
- `buildBlockIndex` 的输出仅取决于 `(project, floorId, floorState.removed, floorState.replaced)`
- 在 canonical search 中，`floorState` 对象通过 `JSON.parse(JSON.stringify(state))` 克隆，相同引用意味着相同的 removed/replaced 集合
- 缓存属性为 `enumerable: false`，不会影响 `JSON.stringify`、`Object.keys`、state key 构建或序列化
- 当 `floorState` 被替换（新对象引用），缓存自动失效（新引用无缓存属性）

数据完全符合 Cloud Review 定义的 **Case C (cache hit 很高，但 key-build 与 cloneJson 吞掉收益，只优化 lookup plumbing)**：
- 缓存命中率已高达 88.6%，但由于在 5.6 万次命中中每次均执行复杂的 `JSON.stringify` 对象键构建，并在返回时调用 `JSON.parse(JSON.stringify(value))`（`cloneJson`），导致仅管道开销就消耗超过 1 秒 CPU 墙钟；
- 审计确认，全库所有调用者对 `evaluateBattle` 返回的 `battle` 对象均为只读访问（只读 `damageInfo.damage`、`supported`、`guards`），不存在任何就地修改。

### 2. 单项优化实现 (`enableFastBattleEstimateCache`)

**文件**: `shared-solver/lib/battle-resolver.js`

1. **直接字符串键构建器 (`buildFastBattleEstimateKey`)**:
   - 彻底避免在 6.4 万次调用中反复分配包含 5 个嵌套对象与数组的中间包装容器；
   - 包含 legacy key 的全部 8 维数据（`floorId`, `x`, `y`, `enemyId`, `hero (hp, atk, def, mdef, lv, hpmax, mana, manamax, equipment)`, `inventory`, `flags`, `floorStates[floorId].removed`, `floorStates[floorId].replaced`），严格保证相同的状态产生唯一的键，不同的状态必产生不同的键。
2. **零拷贝安全返回 (Zero-Clone Direct Return)**:
   - 缓存写入时对 `result` 执行 `Object.freeze(result)`，彻底杜绝任何调用者就地污染；
   - 缓存命中读取时直接返回已冻结对象，彻底消除 5.6 万次 `JSON.parse(JSON.stringify(value))`（节省 ~250ms+）。
3. **全链路开关透传**:
   - `enableFastBattleEstimateCache` 默认为 `true`；
   - 贯穿 `FunctionBackedBattleResolver`、`StaticSimulator`、`isolated-segment-executor.js` 与 `segment-worker.js`，可随时独立关闭回退。
