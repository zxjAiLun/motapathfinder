## Owner request and starting evidence

Owner requested:
1. Complete diagnosis of why solver missed the Boss route while user save achieved HP 337,191 / ATK 72 / DEF 4 (Boss lethal threshold ~143,594 HP, leaving ~193,597 HP).
2. Deploy solver search to cloud server (`cloud1`) and allow real-time monitoring on `http://127.0.0.1:8787`.

Diagnosis findings:
- User save executed **21 floor-flying actions** (`fly:TS13`, `fly:TS12`, `fly:TS14`, `fly:TS11`...) and zero stair transitions between floors across the TS11–TS15 trial.
- Game Start event grants `item:fly = 1` (楼层传送器) and `item:book = 1`, and the S1 trial entry event in JC19 resets stats and regular keys, but does **not** reset `item:fly` or `item:book`.
- Solver configuration `profiles/neko-zero-key.json` hardcoded `initial.inventory = { greenKey: 30 }`, omitting `fly: 1`.
- In `shared-solver/lib/simulator.js`, `canUseFloorFly` checked `hasEnemyLeft(project, state, "E1649")` across all floors of the entire project; in Neko tower, `E1649` ("「闭锁」") exists on endgame floors `K15`, `K16`, `MT780`, causing `hasFlyBlocker` to evaluate to `true` globally and permanently disabling floor flying throughout the tower.
- `dp-search.js` only enumerated primitive walking and stair actions, never calling `enumerateFloorFlyActions`.
- Consequently, previous search runs (including PR-5.32m's 32k attempt) were completely unable to fly between floors to farm required stats and potions, remaining trapped on TS15.

## Bounded design and gates

1. **Tool and item contract**:
   - In `simulator.js`, scope `hasEnemyLeft(project, state, enemyId)` to the current floor `state.floorId` (or allowed search floors), rather than scanning the entire multi-hundred-floor tower.
   - In `simulator.js`, ensure `enumerateFloorFlyActions` emits deduplicated, shortest-path actions per target floor (at most one per valid visited floor).
   - In initial configuration profiles (`neko-zero-key.json` / `neko-one-key.json`), ensure `initial.inventory` includes `fly: 1`, `book: 1`, `I600: 1`, and `protectedSpendLimits: { greenKey: 1 }`.

2. **Search engine integration**:
   - In `dp-search.js`, support `config.includeFloorFly === true` to include `simulator.enumerateFloorFlyActions(state)` in action generation.
   - In `durable-search.js`, forward `includeFloorFly` through `searchSemantics` so execution matches provenance fingerprinting.

3. **Verification gates**:
   - Unit test `check-floor-fly-contract.js`:
     - Assert `canUseFloorFly` returns `true` on TS11–TS15 when hero has `fly: 1`.
     - Assert `enumerateFloorFlyActions` generates valid transitions to visited floors.
     - Assert `dp-search` executes `floorFly` actions and transitions state correctly.
   - Regressions: `check:core`, `check:manifest`, `node --check`.

4. **Cloud deployment & live monitoring**:
   - Package clean bundle with solver and tower root.
   - Deploy to `cloud1` under dedicated probe/run directory.
   - Configure progress dashboard service to monitor the active run on `127.0.0.1:8787`.
   - Validate live HTTP response from `search-progress-server`.
