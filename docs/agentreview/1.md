## mimo 评分

### mimo1：6.5 / 10

优点：

* agent 目录、`agent.json`、`solve.js` 结构都合理。
* 明确只 import `shared-solver/public`，没有直接碰 `shared-solver/lib/**` 或塔内 solver。
* 知道要输出 `route.json / metrics.json / diagnostics.json / agent-report.md`。
* 有多组 fallback 参数，知道 `stopOnFirstGoal: false` 对资源时机很关键。

主要扣分：

* 初稿里有明显拼写/代码细节问题，比如 `atempts.push`、`proofClaim.profLevel`、`actionTrimed` 等，说明实现时容易直接炸。
* 对 `whiteislandTrial` 的处理停在“枚举 Start 事件试试”，没有真正解决 `executeActionList` 不在 public API 的问题。
* 初稿允许 not-found 时不写 `route.json`，这会被 harness 的 required outputs 卡住。mimo2 后面修了这个。
* failure diagnostics 里调用 `summarizeSegmentFailure` 的方式偏含糊，参数和实际上下文不够可靠。

### mimo2：7.4 / 10

mimo2 进步比较明显：

* 它逐项审查了 10 条约束，并确认只写 `agents/mimo-v2.5-pro/agent.json`、`agents/mimo-v2.5-pro/src/solve.js` 和 harness 输出路径。
* 发现 not-found 时不写 `route.json` 会导致 missing output，并改成写最小 route。
* 认识到 `buildRegionProofClaim` 已经内置降级逻辑，计划改为直接使用它，不再重复包装。
* `agent.json` 占位符、边界检查路径、CLI/env fallback 都比较清楚。

仍然扣分的地方：

* **最大问题仍是 whiteislandTrial**。mimo2 的方案还是“createInitialState → enumerateActions → 找试炼间 → applyAction；若公共 API 不支持该事件路径，直接从初始状态搜索”。这个 fallback 很可能不可靠，因为 public suite 当前启用的正是 whiteisland smoke，而它的起点不是普通初始状态。
* not-found 的最小 route 写成 `"kind": "motapathfinder.route.v1"`，而正常 route schema 是 `schema` 字段。harness 可能只检查文件存在，但更严格 evaluator 会认为这不是合法 route record。
* fallback 参数策略还可以，但没有说清楚如何限制总运行时间，可能对 include-disabled 的 onlyup 重任务过慢。

所以 mimo 最终版是“可实现的普通 agent plan”，但不是最稳。

## ds 评分

### ds1：7.0 / 10

优点：

* 比 mimo1 更早抓到了核心问题：`whiteislandTrial` 需要 `executeActionList`，但它不在 public API。
* 有清楚的 fallback strategy：默认、candidateLimit=12、location key、预算翻倍。
* proof claim 降级规则比较完整，能区分 `actionTrimmed`、预算耗尽、time-limit、not-found。
* 失败诊断字段比较完整，包括 `failureClass`、`missingGoalFields`、`segments`、`attempts`。

主要扣分：

* `agent.json` 初稿里 `allowedWriteRoots` 写成了 `agents/depseek-v4-pro/runs`，少了一个 `e`，这会直接影响边界配置可信度。
* 初稿写了 “Total wall time ... 600ms”，明显不合理；后面又写 60s/60000ms，说明计划内部不一致。
* 仍然说 `createStartState` 处理 whiteislandTrial via `executeActionList`，这和“不 import private lib”的约束冲突，虽然它后面提出 fallback subprocess。
* route not-found 处理不够严谨，初稿说 route 只在 found 时写。

### ds2：8.2 / 10

ds2 是四份里最强：

* 它做了 10 条约束审查，明确 PASS：不 import `shared-solver/lib/**`、不 import 塔内 solver、不写塔目录、不硬编码路线。
* 它明确指出 **critical gap：whiteislandTrial start state 需要 `executeActionList`，而 public API 没导出**。这是最关键的发现。
* 它提出 whiteislandTrial 分支直接 spawn `shared-solver/run-region-dp.js`，避免自己用 private API 复刻起点状态。
* 它保留普通 region 任务走 `runMilestoneSearch`，只有 whiteislandTrial 用 canonical subprocess，这个分流设计比 mimo 更现实。
* 失败点和 mitigation 写得比较清楚：subprocess failure 捕获 stderr、not-found 也写四个输出、boundary check 继续通过。

扣分点：

* “spawn canonical `run-region-dp.js`”虽然工程上可行，但对 Agent-from-scratch benchmark 来说有点像**把 enabled public task 交给官方入口代跑**。这会提高成功率，但会削弱 agent 自己的算法含量。
* ds2 第 7 条一开始仍写“route.json either omitted or written as empty/null record”，这和 required outputs 不完全一致；后面 revised plan 又说 always write all 4 files。内部有轻微矛盾。
* 对 `runViaCanonicalSolver` 的 route/metrics/diagnostics “augment” 没有细化，容易变成简单转发，不利于比较模型 agent 的真实能力。
* 如果严格定义“只能 public API，不允许调用 public CLI”，那 ds2 会被扣更多分；但按你之前地基设计，`run-region-dp.js` 是 canonical entrypoint，所以我没有重扣。

## 一句话判断

**ds 比 mimo 强在能识别 whiteislandTrial 起点这个真实阻塞点；mimo 比 ds 稳在边界和输出契约更规整，但它没有真正解决 public API 无法进入试炼间的问题。**
如果现在让它们进入实现阶段，我会优先放行 **ds2**，但要求它补一句：`runViaCanonicalSolver` 只能作为 whiteislandTrial 起点兼容路径，不能把所有任务都简单转发给官方 CLI。
