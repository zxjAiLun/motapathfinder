## 问题与已有证据

5.27e（`ac6b0fe`）第一次让 5.27 planner 自主从 MT1 进入 MT2（40-round ON：depth 41、累计决策 51），
但 owner 复核代码后指出两个 P1 contract 问题，并判 70 次 `cf-d0-path_unlock` 不是 experiment-key reuse bug，
而是「repair 与触发它的失败缺乏因果关联」。

已有证据（来自 `ac6b0fe`，不重跑）：

- 40-round ON：depth 41、累计 51、进入 MT2；OFF 停在 MT1（depth 5、累计 10）。
- 80-round ON：depth 81、累计 91，conversion 停在 1；73 次 repair 中 70 次是 `cf-d0-path_unlock`。

owner 授权范围：两个 correctness repair + 一个很窄的 relevance mechanism。

### 本轮明确不做（NO）

加权资源打分、repair depth 调参、Pareto 调参、candidateLimit 变更、16 个 `ALREADY_ATTEMPTED` 重试修复、
branch cap、pruning、prerequisite horizon、`transport-collapse.js`、retention、guided scheduler、MT4-before-MT3。

## 初始设计

### Phase 0A — effective experiment universe

新增 `evaluateBranchExperiments()`：一个 branch 的可执行实验 = normal alternatives ∪ repair experiments。
返回 `effectiveCanAdvance = normalCanAdvance || repairExperiments.length > 0`。
portfolio selection、monotonic exhaustion、preferred-cohort collapse、final lifecycle sweep 全部改读 effective 值，
不再用 `if (selectedRepair)` 打补丁。

### Phase 0B — 同一 prerequisite identity conversion

repair trigger 保存完整 blocked prerequisite 集合（`sourceNodeId`、`floorId`、`x`、`y`、`kind`、`statusBefore`、
`evidenceBefore`），identity 为 `sourceNodeId|floorId|x,y`。
child replan 后复用 planner 已有的 battle-evidence 对象（不重写 damage 判定），逐 identity 比较：

```ini
converted = before ∈ {unbeatable-at-current-stats, lethal-at-current-hp}
            AND after == viable-at-current-state
```

replan 中不含该 node 时记 `NOT_PRESENT_IN_REPLANNED_ALTERNATIVES`，不算 conversion。

### Phase 2 — battle-relevance gate（极窄）

只允许 `ATK/DEF/MDEF/HP/LV/EXP/equipment` 任一 > 0 的 intent；
额外只明确拒绝 `kind == path/unlock 且 combat delta 全 0`。
money / inventory 一律不误伤；EXP 保留（允许多步准备）。

## 合同与不变量

- monotonic branch exhaustion 不得绕过：branch 只在 normal ∪ repair 都为空时才 exhausted。
- route-free 输入边界不变。
- 不引入 scalar score，不调 Pareto，不改 candidateLimit。
- 80-round 不自动跑（5.27e 已用掉那次 escalation）。

## 结果与决定

### Phase 1 — 5.27e 的 causal gate 重新成立（不是撤回）

同一 prerequisite identity 下，5.27e 那个 `1` **仍然存活**：

```ini
round 7, branch-29 -> branch-33
intent cf-d0-path_unlock
MT2:enemy:3,4:zombie | MT2 | 3,4
before = lethal-at-current-hp
after  = viable-at-current-state
sameIdentity = TRUE
```

同一 record 内 `MT2:enemy:9,4:zombieKnight` 仍是 `lethal-at-current-hp`（未 conversion），
说明 identity 粒度确实在做区分，不是「任意 viable 就算」。

```ini
EXACT_SAME_PREREQUISITE_CONVERSIONS = 1
RESOURCE_REPAIR_CAUSAL_EFFECT = ESTABLISHED_FOR_AT_LEAST_ONE_BRANCH
```

同时 Phase 1 也确认了 owner 的预期形状：34 次 repair 中 **31 次是 `path/unlock`**，
且这些 path unlock 只贡献了这 1 次 conversion。

### Phase 3 — relevance gate 生效，但没有通过 success 门

| 指标 | OFF（broad） | ON（battleRelevantRepairOnly） |
| --- | ---: | ---: |
| path/unlock selections | 31 / 34 | **1 / 17** |
| rejectedByRelevance | 0 | 275（全部 path_unlock） |
| repair kind 分布 | path 31, exp/level 3 | **exp/level 16**, path 1 |
| exact conversions | 1 | **1** |
| max branch depth | 41 | 14 |
| max cumulative decisions | 52 | 24 |
| MT3 | MISS | MISS |

gate 精确地做了它被授权做的事：纯 path unlock 从 31 降到 1，预算改投 `exp/level`。
但 `ON_EXACT_CONVERSIONS` **没有超过** OFF，`MT3_FOUND` 也是 false。

唯一那次 conversion 在两边都是同一个 round 7 事件，而且它本身来自一个 path unlock
（该 intent 带正 HP delta，故在 ON 下仍被放行）——所以 gate 并未削弱既有证据，也没有制造新的。

```ini
RELEVANCE_GATE = TOO_AGGRESSIVE_OR_NOT_SUFFICIENT
```

按 owner 预设：此处 **STOP，不调第二版 filter**。
