## 目标与背景

在 PR-5.24g Combined Formal Run 2 中证实：
- 图块索引记忆化（Iteration 1）+ 战斗估算管道优化（Iteration 2）使 30s 预算内的有效扩展量从 3,025 提升至 4,642 (+53.5% OBSERVED)；
- 首探批处理耗时缩短 35.8%（14.77s → 9.48s），释放约 5.3 秒墙钟；
- 释放的墙钟被全额注入 MT3→MT4 主线探索，使得 MT3→MT4 扩展数翻倍（1,365 → 2,764 扩展），耗时达 13.74 秒；
- 瓶颈已明确转移至 **MT3→MT4 下游规范搜索本体成本**。

PR-5.24h 的目标是：直接针对 **MT3→MT4 这一真实下游瓶颈** 建立固定工作量测试基准，下钻分析其计算开销构成，实施单项安全通用优化。

## 3. MT2→MT3 与 MT3→MT4 每扩展工作量对比与核心归因

对比两者每扩展（per expansion）的结构化指标与耗时分布：

| 指标 (每扩展平均) | MT2→MT3 (520 exp) | MT3→MT4 (897 exp) | 对比与归因 |
|---|---|---|---|
| **Wall 耗时 / expansion** | **21.26 ms** | **11.77 ms** | **MT3 单步扩展反而比 MT2 快近一倍** |
| **CPU 耗时 / expansion** | **22.60 ms** | **12.52 ms** | 同样显著更低 |
| **Battle Resolver 调用 / expansion** | 105.4 次 | 36.6 次 | MT3 上怪物战斗密度相对较低 |
| **Hazard 扫描单元 / expansion** | 3,855 cells | 2,258 cells | MT3 单步危害扫描更少 |
| **Stabilization 通道 / expansion** | 19.7 次 | 11.9 次 | MT3 稳定化震荡更少 |
| **Stabilization 耗时 / expansion** | 14.63 ms | 6.84 ms | 单步稳定化耗时减半 |
| **Primitive 枚举耗时 / expansion** | 2.53 ms | 1.96 ms | 单步枚举耗时更少 |
| **Reachability 耗时 / expansion** | 2.07 ms | 1.42 ms | 单步可达性耗时更少 |

### 核心科学结论：MT3→MT4 为何消耗 13.74 秒？
- **不是“每步扩展变慢”**：数据清晰证实，MT3→MT4 的单位扩展计算成本（11.77 ms/exp）远低于 MT2→MT3（21.26 ms/exp）；
- **瓶颈源于状态空间广度与扩展规模**：
  - MT2→MT3 在 152 步即打通首个目标，全前沿在 520 步迅速收敛耗尽；
  - MT3 地图连通性大、候选多（16 条前史分支），在 30 秒内向 MT4 方向激增探索了 **2,764 次扩展仍未收敛**；
  - 2,764 expansions × 11.77 ms = 约 32.5 秒的累计计算量（经批处理压缩至 13.74s 墙钟）；
- **下一步优化杠杆**:
  - 在 MT3→MT4 的 11.77 ms/exp 中，`stabilization` 仍占 **57.9% (6.84 ms/exp)**；
  - 核心突破口在于 `stabilization` 中占比最高的 `battleScan` (3.28 ms/exp)、`hazardBuild` (1.74 ms/exp) 与 `pickupScan` (1.49 ms/exp)。

## 4. Iteration 1 优化实现与 G28 门禁实测数据

### 4.1 优化实现 (`enableFastCollectTargets`)
- **文件**: `shared-solver/lib/auto-actions.js`, `shared-solver/lib/simulator.js`, `shared-solver/lib/isolated-segment-executor.js`, `shared-solver/segment-worker.js`
- **机制**:
  1. 使用紧凑定长数组与代际计数器重构 BFS 目标遍历 (`collectTargetsFast`)：
     `bfsQueueX`, `bfsQueueY`, `bfsQueueDist`, `bfsVisited`（`Uint16Array`），代际递增 `bfsGeneration`；
     彻底消除 2.1 万次 BFS 中数以百万计的 `new Set()`、`coordinateKey` 字符串与 `{ x, y, distance }` 临时对象分配；
  2. 独立保留 legacy `collectTargetsLegacy`，提供 `enableFastCollectTargets` 独立开关（默认 `true`）；
  3. `state.js` 内部对静态图块定义执行冻结缓存 (`getTileDefinitionByNumber`)，消除全图近百万次 `{ number, ...definition }` 包装分配。
